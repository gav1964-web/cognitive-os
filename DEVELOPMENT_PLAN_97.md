5. Проверить перенос на новую задачу с критериями до inference. Известные репозитории
   считать калибровкой; не выдавать этот пакет за независимую сертификацию 9.7+.

## Критерии достижения

| Утверждение | Действующие основания | Граница |
|---|---|---|
| Узкая семантическая готовность | `runtime/narrow_type_role_semantics.py`: минимум 2 случая и 2 lineage на каждый из двух типов, для holdout также 2 owner; все обязательные проверки, auditable artifacts, реальное изменение, каждая роль ≥9.7 | Не подтверждает все Python-проекты |
| Узкая сертификация | Дополнительно `runtime/narrow_type_certification.py`: все 12 role/type cells eligible, ledger receipt, независимость, no-role-regression, chain continuity, отсутствие stubs, input/semantic evidence | Не даёт source apply или общей production maturity |
| Широкая готовность 9.7 | `config/role_promotion_policy.json`: минимум 80 проектов, pass rate ≥0.97 и перечисленные независимые evidence; применимость к конкретным ролям/типам фиксируется явно | Четыре узких случая не заменяют широкую кампанию |

Narrow evaluator берёт худший score роли по случаям, а не среднее. Бинарные
проверки делают один пропуск существенным: нужно выполнять поведенческие
контракты, а не округлять балл или подгонять поля. Training caps сохраняются.
Минимальная выборка — технический порог, не статистическая гарантия вероятности
успеха 97%. Показывать знаменатель, случаи, ошибки и границы вместе с баллом.

Сравнение direct/short/full — отдельное утверждение о пользе COS.
`evaluation/PROTOCOL_V2.md` требует одинаковую модель, независимого слепого judge
и минимум 20 полных задач / 2 на класс для общего claim. 26 подготовленных inputs
не заменяют 80 проектов и не являются завершёнными сравнениями. Символический
greenfield без LLM пока не соответствует same-model v2. Косметический вызов
модели ради журнала недопустим. Другой вид сравнения требует отдельно объявленного
протокола до запусков, с сохранением прежних правил и истории.

## Этапы и условия перехода

| Этап | Работа | Условие выхода |
|---|---|---|
| 1. Зафиксировать измерение | Снять baseline текущей версии на известных cases с указанием exposure. Проверить rubric/gates на ложном patch и подмене evidence; связать код, policies, inputs, окружение и модель | Baseline воспроизводим; неверные решения отклоняются; train/calibration/holdout разделены до изменения ролей |
| 2. Сквозной причинный ремонт | Взять buffer/stateful дефект, минимизировать вход, воспроизвести baseline, провести диагноз → дизайн → delta → patch → native tests → review | Цепочка доставляет исправление в копии; исходный failing test и regression проходят, исходник неизменен; ассистент не пишет засчитываемый patch за роль |
| 3. Укрепить слабые переходы | Исправлять первый разорванный переход; проверять другие функции/проекты и контрпримеры. Предлагаемый пилот: 6 CLI + 6 library development/calibration cases разных семейств | Рабочая цепочка, отклонение неверных patch, отсутствие регрессий и скрытых вмешательств; пилот не выдаётся за сертификат |
| 4. Новый независимый narrow holdout | Заморозить версию и ранее не раскрытые случаи; evaluator не пишет решение; oracle скрыт до окончания попытки; сохранить все артефакты | Все шесть ролей ≥9.7 в обеих группах, выполнены semantic и certification gates; утверждается только подтверждённый scope |
| 5. Устойчивость и польза | Повторить на новом наборе; проверить окружения, лимиты, fallback и controlled stop. Отдельно — корректный direct/short/full эксперимент | Нет скрытых провалов; вывод о пользе опирается на сопоставимые задачи, расходы и вмешательства |
| 6. Расширение области | Последовательно framework/plugin → сервисы и async/I/O → SDK/external process → сложные приложения. Researcher — отдельная ветка | Новые role/type cells измеряются заново; широкая готовность требует собственных gates |

Зависимости: **1 → 2 → 3 → 4 → 5 → 6**. Окружения и сбор расходов можно готовить
одновременно с ремонтом. Неизвестная стоимость не блокирует функциональные тесты,
но блокирует достоверный cost claim. Срок 9.7+ не обещается: свежие qualified cases
и независимое судейство пока не обеспечены. Контроль — по завершённым этапам.

| Analyzer | Связать сбой с вызовами, состоянием и target; отделять факты от гипотез; reducer сохраняет failure signature | Минимальный пример, source refs и причинный диагноз; чистый/неподходящий проект не объявляется дефектным |
| Architect | Выбирать ремонт из диагноза; различать existing-project/greenfield; сравнивать ограниченные альтернативы и контрпримеры | Target внутри разрешённого scope; дизайн объясняет изменение поведения и имеет исполнимый путь к patch |
| SpecWriter | Связать каждое требование с действием, контрактом и acceptance; фиксировать ошибки, эффекты и invariant | ImplementationDelta с файлами/символами, pre/post conditions и командами; generic spec не получает статус готового ремонта |
| Implementer + Programmer Executor | Получать реальный patch из delta; расширять семейства ремонтов по evidence, ограничивать область и попытки | Patch без upstream fix проходит targeted/native tests; несовместимый случай даёт конкретный controlled stop, а не заглушку |
| Tester | Проверять baseline → patched на неизменённом тесте; добавить внешние negative/edge cases и неверные patch | Неверное исправление отклоняется; есть regression и сохранение inputs/исходников/outputs; supplied и generated tests различимы |
| Reviewer | Сопоставлять diff, требования, тесты, hashes и interventions; не доверять одному status=ok | Отклоняются пропавшие тесты, подмена artifact/model, source mutation и ложный успех; approved связан с проверенным изменением |
| Researcher | Находить проверяемые причины пробела, пригодные cases и нужную документацию; сохранять provenance/exposure | Отдельная рубрика проверяет точность источников, полезность для следующего patch и корректный отказ; чужие ролевые баллы ему не присваиваются |

Приоритет — **причинный диагноз → конкретный delta → исполняемый patch**.
Дополнительные отчёты Tester/Reviewer без такого результата не устранят
наблюдаемую причину низких баллов. Эти роли сразу нужны как проверки против
ложного успеха при доработке первых четырёх.

## Корпус и независимость

- Granny/Rosbags ранее qualified, но hashes, пригодность и отсутствие exposure
  для нового holdout проверяются заново. Qualified не означает blind.
  Независимые библиотечные случаи остаются отдельным пробелом.
- Task15 и известные replay оставить regression/development cases. Новый prompt
  вокруг известного исправления не делает случай свежим.
- Разделять проекты, lineage/forks, владельцев и семейства дефектов. После просмотра
  oracle или ручного ремонта случай потреблён: повтор — regression, для независимой
  проверки нужен новый случай. Первая неудача остаётся в результатах.
- Фиксировать первую попытку, bounded retries и помощь ассистента отдельно.
  Правка COS между попытками означает новую замороженную версию, а не обновление
  успешности старого receipt.
- Независимый judge не разрабатывает решение. Другая модель сама по себе не
  обеспечивает независимость: нужен раздельный доступ к oracle/inputs/ключу.

## Отчёт после каждого этапа

Таблица role × project/type: score, дата, source/policy digest, split/exposure,
полнота evidence и проваленный gate. Отдельно: accepted/attempted tasks,
controlled stops, environment/provider failures, manual interventions, input/output
tokens, стоимость и время. Для skipped/environment-blocked не ставить качественный
ноль и не исключать их молча из статистики попыток. Формулу pass rate фиксировать
до кампании. Предлагавшиеся 6+6 случаев пилота — рекомендация этого плана, не
новое правило сертификации и не изменение действующей policy.

Различать состояния: **implemented → regression verified → transfer observed →
narrow holdout passed → scoped certified → broad validated**. Только нужное
evidence переводит результат на следующий уровень.
