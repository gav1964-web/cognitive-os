# Задачи для следующего этапа разработки

Последний [внешний пакет](docs/architecture/external_cycle_20260918.md): один
принятый ремонт после feedback, 81 native tests. Два модельных предложения новых
тестов отклонены; смысловые ошибки описаний сохраняются. Пакет закрыт:
10 calls / 41054 tokens / unknown0. Независимых оценок 9.7+ нет.
Следующие действия — [план](DEVELOPMENT_PLAN_97.md). Автоматизация передачи
regression feedback, достаточность acceptance и проверка финального текста
записаны в очереди; повторное напоминание владельца не требуется.
Исторический неизвестный расход предыдущей GigaChat-кампании сохраняется.

Постоянная очередь — [DEVELOPMENT_TASKS.json](DEVELOPMENT_TASKS.json).
Она хранится вместе с проектом, отдельно от очищаемых артефактов. Пустая очередь
означает отсутствие зарегистрированных задач этого контура, а не отсутствие
любых проблем в COS. Общий план остаётся в DEVELOPMENT_STATUS.md.

Теперь очередь содержит и общие инженерные задачи: `test_failure`, `architecture`,
`documentation`, `provider`, `evaluation`, `feature`. У них есть приоритет 1–3,
зависимости и явное поле `blocking`; по умолчанию это неблокирующий backlog.
Проверка размера обновляет только свои записи и сохраняет остальные. Управление:
`python tools/development_stage.py task --help`, закрытие с доказательствами:
`python tools/development_stage.py close --help`. Полный рабочий процесс и память
решений описаны в [development_workflow](docs/architecture/development_workflow.md).

В начале работы ассистент читает очередь, проверяет актуальность открытых задач
и самостоятельно выполняет относящиеся к текущему этапу работы в разрешённой
области. Для общего «продолжай разработку» открытые задачи являются входящим
планом: сначала нарушения размера и падения исходных тестов, затем проверка
ручных исправлений. Напоминание пользователя не требуется. При узком запросе
задачи других подсистем сохраняются для следующего подходящего этапа.

По указанию владельца от 17 сентября 2026 продолжение выполняется пакетами
по пять содержательных шагов с общим отчётом. Тесты и оформление отчёта входят
в каждый шаг и не считаются отдельными достижениями. Между шагами не требуется
подтверждение; остановка нужна при отсутствии необходимого доступа, существенного
решения владельца или допустимого бюджета.

Новое указание владельца от 17 сентября 2026: следующие пакеты выполнять без
отдельного подтверждения LLM-вызовов, если суммарный расход пакета (вход и выход)
остаётся строго меньше 1000000 токенов. Это постоянное разрешение заменяет прежние
пометки «нужен новый бюджет» для таких пакетов; старые завершённые серии не
возобновляются и их результаты не переписываются. До запуска фиксировать число
запросов, входы, лимиты выхода и консервативный резерв; учитывать всю серию,
не каждый запрос отдельно. При неизвестном расходе или невозможности удержать
пакет ниже порога остановить дополнительные вызовы. Порог не является целью
расхода: использовать минимальный осмысленный эксперимент.

`tools/project_context.py --list` показывает число открытых задач; контекст
подсистемы включает относящиеся к ней записи и ссылку на всю очередь.
Это передача контекста между запусками ассистента, не фоновый запуск агента.

## Автоматическое пополнение

Обычный финальный запуск `tools/finalize_stage.py` обновляет очередь после
завершения операции, включая остановки до создания sandbox. Повторный запуск
не дублирует задачу: ID привязан к относительному пути. Хранятся хеш и размер
исходника, причины ограничения оператора, результат последней попытки,
регрессионный scope, ссылки на проверки и конкретное следующее действие.
Поле `notes` предназначено для выводов ассистента и сохраняется при обновлении.
В заметках нужно оставлять решение, затронутые контракты и следующий шаг,
не исходный код, секреты или полный ответ провайдера.

Черновая фаза не записывает промежуточные превышения в очередь. Программный
API `finalize_stage()` сам по себе её не меняет: пилоты и проверочные снимки
не создают задачи в рабочем COS. Для отдельного read-only аудита есть
`--no-handoff`; обычное завершение этапа выполняется без этого флага.
Сбой записи очереди делает CLI неуспешным и не затирает прежние записи.

## Как завершать задачи

- `open`: превышение остаётся; ассистент исследует зависимости и выполняет
  обычный рефакторинг, если оператор не поддерживает нужную структуру.
- `needs_verification`: размер уже допустим, файл удалён или вышел из области
  аудита. Нужно проверить вызывающий код, imports и регрессии. Уменьшение числа
  строк, удаление файла или ослабление лимита сами по себе не закрывают задачу.
- `resolved`: автоматический перенос применён с проверками и совпадающим хешем
  sandbox либо ассистент завершил ручной review и записал его доказательства.
  Новое превышение по тому же пути снова открывает запись.

После ручного исправления ассистент выполняет относящиеся к изменению тесты,
сохраняет receipt, затем редактирует соответствующую запись JSON:
`status = "resolved"`, `next_action = "none"`, а в `resolution` записывает
`kind = "assistant_review"`, `source_sha256` текущего файла (или `null` при
проверенном удалении), `evidence` со списком путей к receipts, `summary` с
обоснованием и `resolved_at` в UTC. Это утверждение ответственного ассистента
о выбранных проверках, не автоматическая сертификация поведения. Для удалённого
файла обязательно проверить imports/потребителей. Старые notes и last_attempt
не удаляются. Нельзя закрывать задачу только ради успешного gate.

После этого повторно выполнить финализатор. При открытых блокирующих задачах CLI
не считает этап завершённым даже при отсутствии превышений. Необязательный backlog
остаётся видимым, но не блокирует другие этапы. Если работа
упирается во внешний сбой, записать проверенный факт и следующий ограниченный
шаг в notes; не выполнять бесконечные повторы и не выдавать остановку за успех.
