# GeminiVM: общий предел времени запроса

23 сентября 2026. После native-приёмки сохранённого humanize-кандидата следующий
этап ограничивает полный запрос и проверяет один полезный проход через COS и5.

`Provider.ask` создаёт один монотонный бюджет `request_timeout`, по умолчанию
1500 секунд. Он охватывает подготовку VM/браузера, все отправки, продолжение `?`,
получение ответа и источников. Повтор, diagnostic probe и shallow-copy worker
не создают новый бюджет. Локальные response_timeout/followup_timeout остаются
верхними пределами отдельного ожидания и ограничиваются оставшимся временем.
Рабочая конфигурация: request1500с, response1200с, followup300с;
внешние лимиты шлюза1800с и профиля COS1860с остаются больше общего бюджета.

`DeadlineTransport` ограничивает каждый SSH-вызов минимумом собственного лимита
команды и остатка бюджета; ограниченные паузы используют тот же clock.
По истечении бюджета возвращается HTTP504 `request_timeout`. Частично полученный
или поздний ответ не выдаётся за успех; дополнительные действия и даже снимок
экрана после отказа не запускаются. Последние уже записанные кадры сохраняются.
Шлюз5 сохраняет этот код и не помечает его как разрешение повторить запрос.
COS сохраняет pending task, источник и причину отказа без оценки качества роли.

Это кооперативное ограничение I/O: локальная запись receipts, планирование ОС
и завершение subprocess могут добавить небольшие накладные расходы. Уже отправленная
генерация на стороне Gemini может продолжиться; таймаут не нажимает Stop и
не гарантирует отмену удалённой вычислительной работы. Автоматические способы
восстановления не расширены. Бюджет независим для каждого нового HTTP-запроса.

Диагностика GeminiVM содержит request_timeout_seconds и elapsed_seconds.
Шлюз сохраняет прежний ограниченный набор метаданных; полные времена доступны
в receipt провайдера, время HTTP — в COS telemetry. Счётчики retries по-прежнему
описывают начатые попытки, фактические отправки проверяются по events.

Проверки до живого запроса:409 GeminiVM tests (21 новый сценарий),4 gateway tests,
29 COS tests. Добавлены случаи истечения во время preflight, ожидания, `?`,
empty-page retry, diagnostic probe, копирования ответа и источников; отдельная
ошибка response_timeout сохранена. Проверены терминальный504 и отсутствие
скрытого повтора в адаптере шлюза. Исходники установлены после проверки SHA256
и400 строк; оба сервиса перезапущены. Машинные YAML не менялись.

Evidence: `artifacts/geminivm_deadline_20260923/installed.json`, `tests.xml`,
`gateway-tests.xml`, `cos-tests.xml`, `staged/`, `gateway-staged/`.

Живой scope: один запрос `geminivm/pro` на ранее отвергнутый ремонт публичного
add-trailing-comma с сохранением форматирования независимых фрагментов.
Исходный повтор:127 passed /7 failed /1 xfailed; кандидат проверяется на том же
наборе без ручной правки. Это известная задача с feedback, не независимая оценка
трёх ролей. Humanize повторно не предъявляется; usage Gemini Web неизвестен.

Первый запуск заблокирован автоматической проверкой разрешений до отправки.
Проверка происхождения payload сопоставила пять исходников с локальным Git-коммитом
публичного репозитория; ещё два файла — синтетические assertions. Приватные
исходники COS/шлюза и машинные настройки не включались. Анонимная загрузка
raw.githubusercontent.com завершилась TLS timeout, поэтому удалённое совпадение
не заявляется. После представления локальных доказательств повторная проверка
разрешений допустила один запрос. Evidence: `payload-provenance.json`, `live/protocol.json`.

## Результат одного живого запроса

`20260923T003501-3a44b8ea8c71`: один HTTP через COS→5→GeminiVM, две браузерные
отправки (исходная задача и один `?`), Pro подтверждена. Первая попытка дала
service_error, продолжение автоматически получило новый ответ в том же диалоге.
Время провайдера459,422с, весь HTTP-цикл462,265с; предел1500с не исчерпан.
Результат: «Я не могу помочь вам с этим, я просто языковая модель.»
Кандидата нет, native-ремонт не принят, оценки ролей не повышаются.
Это подтверждение доставки продолжения без ручного вмешательства, не полезности
ответа и не живое доказательство срабатывания deadline (его проверяют тесты).

Прежний классификатор ошибочно присвоил этой короткой фразе normal; COS сохранила
ошибку JSON. Исходные response/summary не изменены. В GeminiVM добавлен узкий
whole-response шаблон отказа; цитата этой фразы и полезный текст после неё
не совпадают. Проверка сохранённого ответа offline проходит через реальный
классификатор, адаптер шлюза и обработчик evidence COS: refusal→HTTP422→
quality_evaluation=not_evaluated. Новых HTTP/LLM-вызовов нет.
После этого418 тестов GeminiVM прошли (ещё9 сценариев), исправление установлено,
сервис8002 перезапущен. Новый живой запрос с финальным классификатором не выполнялся.
Evidence: `tests-final.xml`, `installed-final.json`, `offline-outcome.json`,
`live/http-response.json`, `live/summary.json`, `live/provider-run.txt`.

Практический вывод: общий предел и доставка восстановления работают в проверенных
границах, но GeminiVM Pro пока нельзя считать надёжным единственным маршрутом
первых трёх ролей. Следующий этап должен улучшать долю принятых задач и время
всего цикла; повторять этот prompt или расширять цепочку UI-обходов не следует.
