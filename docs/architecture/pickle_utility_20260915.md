# Проверка пользы pickle-плагина

15 сентября 2026. Четыре новых локальных development-случая, составленных
ассистентом для проверки границ механизма. Это не внешний проект, не blind
holdout и не независимое измерение ролей. Рабочий код и активная KB не изменены.

## Протокол и результат

До запуска зафиксированы исходники случаев, три теста каждого случая, рецепт,
hash исходного COS и hash runner:
`artifacts/verification/pickle_utility_20260915/manifest.json`, `freeze.json`,
`source_inventory.json`. Рецепт задан явно, автоматически не выводится.
Сравниваются сохранённый генератор до миграции, typed API плагина и вызов через
registry. Во всех трёх вариантах получены одинаковые байты предложений/отказы.

| Случай | Исходные тесты | После предложения, каждый маршрут | Вывод |
|---|---|---|---|
| Два сохранённых обязательных аргумента | 1/3 passed | 3/3 passed | Механизм исправляет случай |
| Дополнительный `retryable=True` с default `False` | 1/3 passed | 2/3 passed | Кандидат теряет состояние, полный контракт не выполнен |
| Уже существующий `__reduce__` | 3/3 passed | Отказ от правки, 3/3 passed | Сохранено исправное поведение |
| Значения аргументов преобразованы перед сохранением | 1/3 passed | Отказ от правки, 1/3 passed | Неподдерживаемый случай остаётся неисправленным |

Тесты выполняют настоящий `pickle.dumps/loads`, проверяют весь `__dict__`,
тип, сообщение, `Exception.args` и исходное поведение конструктора. Каждый
результат проверен трижды в новых каталогах. Всего 40 pytest-процессов: четыре
baseline и 36 проверок маршрутов. Падающие проверки — измеренные исходы кандидатов,
а не принятые исправления. LLM и финальная ролевая цепочка здесь не запускались.

Причина потери состояния видна в предложенном `__reduce__`: он воспроизводит
только два `required_constructor_inputs`; необязательный `retryable` получает
значение по умолчанию. Ошибка присутствует и в сохранённом генераторе до миграции.
Показатель уверенности active KB не доказывает сохранение всего контракта.
Результат: один исправленный из трёх исходно неисправных случаев у всех маршрутов;
прироста качества от самого переноса не обнаружено.

## Время и границы измерения

Медиана девяти вызовов после первичного обращения, с чередованием маршрутов:

| Случай | Прежний генератор, мс | Typed API, мс | Registry, мс |
|---|---:|---:|---:|
| Обязательные аргументы | 0.165 | 0.122 | 23.341 |
| Необязательное состояние | 0.194 | 0.143 | 26.127 |
| Готовый reconstruction hook | 0.067 | 0.064 | 28.103 |
| Преобразованные аргументы | 0.119 | 0.092 | 26.577 |

Registry проверяет manifest, lint, code/KB hash, схемы, lifecycle и import origin;
typed/legacy API этих дополнительных проверок не выполняют. Это сравнение
различных гарантий вызова, не доказательство неизбежной медленности плагинов.

Медианы трёх циклов «явный рецепт → предложение → три pytest-проверки» составили
примерно 463–577 мс. Разброс запуска subprocess маскирует небольшую разницу;
трёх повторов недостаточно для вывода о стабильном полном времени. Поиск причины,
вывод рецепта, LLM, длительное сопровождение и production-нагрузка в замер
не входят. Модельных вызовов 0; экономия inference не измерялась.

## Локальность изменения знаний

В отдельной копии плагина состояние каталога изменено с active на absent.
Прежняя регистрация отклонена по hash; после регистрации новой копии тот же
процесс вернул staged profile вместо active. Код плагина, общий runtime и
рабочая KB сохранили исходные hashes. Это подтверждает локальное обновление
знания с явной регистрацией, но не доказывает удобство любого будущего изменения
или улучшение предметного алгоритма.

Основной результат: `artifacts/verification/pickle_utility_20260915/result.json`.
Локальная KB: `artifacts/verification/pickle_utility_20260915/local_kb/result.json`.
Контрпример: `artifacts/verification/pickle_utility_20260915/optional_state/registered-0/result.xml`.

## Следующая работа на момент замера

Сначала уточнить локальный контракт pickle: сохранять дополнительное состояние
либо явно отказываться от неподдерживаемой формы до выдачи кандидата. Проверить
positional/keyword-only defaults, `args`, дополнительные атрибуты и существующие
hooks; не переносить вывод из одного случая на все исключения. Затем повторить
сохранённый набор и профильную регрессию, после чего проверить внешний
development-случай. Admission, native acceptance и Reviewer сохраняются.

Массовую миграцию следующих KB пока не начинать: структурная граница подтверждена,
ближайшая польза должна появиться от улучшения самой компетенции. Оптимизацию
registry выбирать после профилирования нужного рабочего потока, с сохранением
обнаружения изменений KB/кода. Подготовленный Toml-sort эксперимент остаётся
отдельной задачей; его бюджет этим замером не использован и не расширен.

Последующее уточнение пользователя: текущая цель — разделение функционала,
поэтому отсутствие прироста качества не блокирует следующий проверенный перенос.
Предложенное выше ожидание прироста перед миграцией отменено.
[Отдельная правка pickle 0.1.1 и действующие критерии](pickle_state_20260915.md).
