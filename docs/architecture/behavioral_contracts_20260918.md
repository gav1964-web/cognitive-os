# Поведение кандидата и успешный результат API — 18 сентября 2026

Пакет из пяти работ. Шлюз проверен штатным bootstrap до inference, оставался
запущенным. Основные результаты: выявлена потеря контрактов вызываемых методов
в ремонтном контексте; добавлена явная проверка возвращаемого успешного статуса.
Принятого ремонта нет. Полное сравнение описаний не завершилось из-за timeout.

## 1. Проверка объяснения предыдущего кандидата

Исходный падающий native-тест выполнен с трассировкой предыдущего кандидата.
Добавленное условие проверялось, но его тело не исполнялось: `items_len=0`,
`footer_len=1`, тогда как условие требовало пустой footer. До него уже выполнялись
оба старых пути вывода комментария. Это контрпример к объяснению кандидата,
не доказательство недостижимости ветки для всех входов. Исходники корпуса сохранены.

## 2. Причинный маршрут и сохранение контекста

Вместо повторения direct-запроса выполнена одна серия hypothesis → candidate:
с прежней проверенной номинацией координатора, source-bound наблюдениями,
предыдущим native-контрпримером и планом выполнения двух исходных assertions.
Модель приняла свою гипотезу с confidence0.85, но снова ошиблась в структуре
контейнера: новый патч проверяет `original.body[0]` как Comment. Сигнатура
непосредственного потребителя описывает элементы как пары ключ–значение.

При разборе обнаружен дефект подготовки контекста COS: диагностическая проекция
сохраняла цель и вызывающие методы, но удаляла тела остальных методов вместе
с их интерфейсами. Теперь сигнатуры непосредственных вызываемых методов остаются
в `source_interface`; их тела явно помечены как опущенные. Аннотация является
декларацией исходника, а не доказанным runtime-типом.

Это исправление выполнено **после** нового модельного ремонта. Offline-подготовка
следующего запроса проверила сохранение tuple-интерфейса и прежний лимит контекста.
Нового модельного вызова с исправленной проекцией не было; нельзя приписывать
этому изменению измеренный прирост качества ремонта.

## 4. project_description0.15.0

Новый opt-in `return_field_equals_for_inputs` связывает конкретный вызов API,
поле возвращаемого словаря и ожидаемое значение до ответа модели. Применяется
тот же ограниченный Boolean/None-анализ с литеральными defaults. Ожидаемое
значение — строка, Boolean или None; сравниваются значение и тип. Нормальный
возврат error-status больше не принимается за выполнение успешного критерия.

Модель не выбирает критерий сама. Неизвестные вызовы остаются unknown; отождествление
поля результата с реальным внешним эффектом остаётся ответственностью рецензента.
Контрпример/unknown может понизить supported до uncertain; автоматической
смысловой сертификации нет. Прежние двенадцать receipts повторно валидируются.

В том же плагине добавлен `api_contracts`: для явно выбранных функций и актуальных
Python-файлов строится ограниченная карта defaults, вызываемых функций, guards,
обработчиков исключений и возвращаемых словарей. Поддержаны прямые функции,
`from`-импорты и aliases; shadowing, неизвестные зависимости и атрибутный dispatch
не разрешаются. Код не исполняется. Карта не доказывает достижимость, динамическую
диспетчеризацию или успешность всей операции. Все лимиты/сокращения явные.

Карта Replay связывает публичный вход с `prepare_environment` и
`validate_environment_profile`. Нет веток по имени проекта или специальной KB
Replay: механизм работает по синтаксису и данным исходников. Алгоритмы, политика
и схемы принадлежат плагину; runtime сохраняет связывание и orchestration.
