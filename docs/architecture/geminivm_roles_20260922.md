# GeminiVM Pro для первых трёх ролей — 22 сентября 2026

Выбор владельца: Analyzer, Architect и SpecWriter используют `geminivm/pro`
через Gateway5 (`http://127.0.0.1:8000/v1`). Профиль `geminivm_pro` и таблица
`role_profiles` находятся в `config/llm_profiles.json`; разрешение маршрутов —
`runtime/role_inference.py`. Общие L4.5/finalizer и настройки остальных ролей
сохраняют независимость. Отдельное описание проекта (`project_description`)
также переведено на Pro.

## Где модель участвует

| Роль | Вызовы и границы |
| --- | --- |
| Analyzer | Сигналы L3.5 и интерпретация L4 поверх фактов сканирования. Для L4 сохраняется требуемая контрактом метка `external_l4`. |
| Architect | Совет по существующим вариантам; новые варианты/источники не принимаются. |
| SpecWriter | Арбитраж только для близких слабых кандидатов; однозначный выбор остаётся детерминированным. |

Настройка SpecWriter передаётся в первоначальный build и повторный build после
обратной связи исполнения. Владение знаниями и полномочия интерпретаторов не
меняются. Назначение модели не означает обязательный вызов на каждом шаге.

## Запуск и настройки

`tools/role_pipeline_run.py --project-dir PATH --goal TEXT` включает три профиля
по умолчанию и проверяет/запускает управляемый шлюз существующим bootstrap.
Сам шлюз отвечает за автозапуск GeminiVM на8002. `--no-role-llm` возвращает
прежний режим; это не обещание полностью offline-исполнения старого Analyzer.
Библиотечный API совместим: включение через `use_role_llm=True`; явные
`analyzer_config`, `architect_advisory_config`, `spec_writer_advisory_config`
имеют приоритет. Greenfield с этими конфигурациями явно отклоняется как пока
неподдержанный режим, вместо молчаливого игнорирования.

Переопределения независимы: `COGNITIVE_OS_ANALYZER_MODEL`,
`COGNITIVE_OS_ARCHITECT_MODEL`, `COGNITIVE_OS_SPEC_WRITER_MODEL` и аналогичные
суффиксы `_BASE_URL`, `_TIMEOUT`, `_API_KEY_ENV`. Общий `COGNITIVE_OS_L45_MODEL`
не меняет эти три маршрута. Для описания проекта сохраняется прежний приоритет
переменных DESCRIPTION/L45 и явной конфигурации.

COS timeout1860с превышает таймаут адаптера Gateway5 в1800с; GeminiVM имеет
собственное ожидание ответа1200с. Это верхние пределы одного запроса.
`response_format=false`: адаптер web-интерфейса его не поддерживает. COS просит
JSON в сообщении и разбирает/проверяет полученный объект. Запрошенный output
budget32768 передаётся клиентом, но GeminiVM не умеет его обеспечивать и не
возвращает токены: фактический расход остаётся неизвестным.

Для этих профилей нет скрытой замены Pro другой моделью. При отказе сохраняется
детерминированный результат с признаком fallback. SpecWriter повторяет запрос
только при ошибке формата уже полученного ответа; busy, отказ, HTTP/transport
ошибки не запускают форматный retry. Один браузер обслуживает запросы
последовательно, другие процессы могут получить busy409.

`role_inference` в результате и записанном отчёте содержит назначенные маршруты
и события с ролью, requested/reported model, latency, известным usage и
ограниченными сведениями gateway. `quality_evaluation=not_evaluated` отделяет
работу транспорта от оценки качества. Отсутствующий usage не считается нулём.

## Проверка

`tests/runtime/test_role_inference.py` проходит реальные точки потребления и
JSON HTTP-клиент с подставленным ответом транспорта: два вызова Analyzer,
Architect, отдельный допустимый арбитраж SpecWriter, CLI bootstrap, приоритет
конфигураций и отсутствие повтора после отказов. Это offline-проверки.
Регрессия:142 теста прошли (`artifacts/role_pro_20260922/tests.xml`).
Живой прогон: один запрос Analyzer,4991 байт входа,108.08с. Gateway5 сообщил
requested/resolved model=pro, browser_model=Pro и HTTP503 provider_error.
GeminiVM run `20260922T035652-e8dc295f52f6` завершился `UI state: UNKNOWN`
после submit_prompt. На сохранённом кадре000012 виден ответ Gemini с JSON
signals, но провайдер не извлёк и не вернул его в COS. Следовательно, это сбой
распознавания/получения ответа, а не доказательство отсутствия генерации.
Точная причина несовпадения UI-маркеров пока не установлена.

Пилот имел максимум4 последовательных запроса и остановил внешние вызовы после
первой ошибки. Architect/SpecWriter в этом живом запуске через модель не
проверены; `status=ok` отчёта обозначает завершившийся fallback-пайплайн.
Это не успешный прогон Pro и не оценка качества. Evidence:
`artifacts/role_pro_20260922/calls.json`, `pipeline.json`,
`provider-response.json`, `provider-final.png`.
До следующего живого сравнения нужен отдельный ремонт UI-распознавания GeminiVM
с replay этого кадра и проверкой длинного ответа. Новая оценка ролей не выставляется.
