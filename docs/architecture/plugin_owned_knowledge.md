# Владение знаниями плагинами компетенций

Принято пользователем 15 сентября 2026. Статус: целевая архитектура и правило
дальнейшей разработки. [Первый pickle-пилот](pickle_competency_20260915.md)
выделяет рабочий механизм; миграция остальных знаний ещё не завершена.

## Границы ответственности

Самостоятельная компетенция объединяет алгоритм, собственную KB, условия
применимости, контракты, тесты и ссылки на доказательства. Единица выделения —
проверяемый механизм для класса задач. Связанные факты и правила могут жить
в одной компетенции; отдельный плагин на каждую запись KB не требуется.

У каждого предметного знания один явный владелец. Его рабочее представление
версионируется вместе с использующим его кодом. Новые предметные правила и
специальные алгоритмы добавляются в соответствующую компетенцию. Общая предметная
KB по мере миграции выводится из рабочего маршрута.

| Компонент | Ответственность |
|---|---|
| Плагин компетенции | Предметные алгоритмы, локальная KB, диагностика, применимость, условия отказа, предметные проверки |
| Каталог компетенций | ID, версии, контракты, зависимости и декларативные признаки поиска подходящих плагинов |
| Общее ядро | Протокол вызова, маршрутизация по метаданным и результатам применимости, разрешение конфликтов, исполнение и проверка контрактов |
| Общий интерпретатор, если нужен | Семантика общих конструкций языка правил без предметных ID, специальных каталогов и веток компетенций |
| Контекст задачи | Факты текущего проекта и наблюдения с происхождением, доступные участвующим плагинам |
| Журнал доказательств | Версии участников, входы, результаты и ссылки на исходные receipts |
| Исследовательские материалы | Кандидаты без рабочего допуска; после проверки получают владельца и область применения |

Плагин может использовать общий интерпретатор для своей декларативной KB или
реализовать специализированный алгоритм обычным кодом. Сложную предметную
процедуру не следует прятать в расширениях общего интерпретатора.
Каталог и маршрутизатор не должны становиться второй предметной KB: сложную
проверку применимости выполняет сам владелец через общий контракт.

## Контракты и совместное использование

Компетенция явно возвращает результат, неприменимость или недостаточность данных.
Совпадение поисковых признаков не даёт права применять механизм. Неоднозначность
разрешается по общему протоколу, включая получение новых данных, LLM или остановку;
специальные ветки по именам компетенций в ядре не добавляются.

Другие плагины получают знание или результат его применения через версионируемый
контракт владельца. Прямое чтение чужих внутренних файлов KB и независимые
редактируемые копии одного правила не являются целевой интеграцией. Кеш результата
допустим только с идентичностью версии/входов и явной политикой актуальности.
Для повторно используемого механизма можно выделить отдельную компетенцию.

Новый плагин в рамках существующего протокола добавляется без изменения ядра
и общего интерпретатора. Расширение самого протокола оформляется отдельно.
Плагин владеет предметной проверкой, но не может сам себе выдать полномочия
применения патча или заменить независимую проверку результата. Существующие
ограничения исполнения, native regression, provenance и Reviewer сохраняются.
Лимит 400 строк применяется к каждому Python-файлу; плагин может содержать
несколько осмысленных модулей.

## Порядок миграции

Первый кандидат — восстановление исключений через pickle. До пилота
`runtime/project_development_boundary_interpreter.py` содержал специальную
загрузку `exception_pickle_reconstruction_patterns.json` и предметный overlay;
исполняющая и проверяющая логика была распределена по `runtime/exception_pickle_*.py`
и `runtime/programmer_exception_pickle_patch.py`. Это исходная точка аудита,
а не уже установленная полная граница владения.

1. Составить карту конкретных записей, функций, потребителей и проверок pickle;
   зафиксировать hashes, действующие контракты и исходные положительные,
   отрицательные и неподдерживаемые случаи.
2. Выделить компетенцию с локальной KB на существующей инфраструктуре плагинов.
   Проверить покрытие KB версией/хешем, загрузку и обновление кешей. Если текущего
   API недостаточно, явно описать минимальное расширение до его реализации.
3. Перевести потребителей на контракт владельца; убрать pickle-ветки из общего
   интерпретатора. Временные адаптеры делегируют владельцу и перечисляются с
   условиями удаления; второй редактируемый источник знаний не сохраняется.
4. Подтвердить эквивалентность результатов, отказов и полномочий на сохранённых
   случаях, отсутствие регрессий и предметных зависимостей в общем слое.
   Отдельно проверить неизвестную компетенцию через тот же протокол без правки ядра.
5. Продолжать перенос следующих знаний по карте владельцев после проверки
   разделения и сохранения поведения. Рост качества и новые внешние benchmarks
   не являются условием такого переноса; улучшения алгоритмов проверяются отдельно.
   Не удалять общую KB
   до проверки всех оставшихся потребителей. Исторические доказательства сохранять.

Это принятый способ организации разработки. Рост точности, снижение стоимости и
упрощение изменений требуют измерений; перенос файлов и успешные harness-тесты
сами по себе не повышают оценки ролей. Миграция выполняется ограниченными этапами
и не становится автоматическим блокером для остальных продуктовых задач.

Уточнение пользователя 15 сентября: на текущем этапе цель — разделение
функционала. Достаточные критерии: один владелец знания, предметно нейтральный
общий слой, проверенные контракты и отсутствие регрессий. Найденные дефекты
оформляются и исправляются отдельными изменениями; отсутствие прироста точности
не считается неудачей разделения и не останавливает следующий проверенный перенос.
