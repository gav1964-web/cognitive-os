# Сравнение стратегий описания после аудита

18 сентября 2026. Пользователь принял пересмотр процесса: измерить пользу уже
созданных механизмов и вернуться к результату разработки. Общий победитель
не установлен; расширение проверок описания отложено. Новых продуктовых
возможностей и роста ролевых баллов этот этап не подтверждает.

## Что сравнивали

Для Replay и Inspect заранее зафиксированы исходники, семь критериев и правило
выбора. Один простой запрос создаёт черновик; полный и адресный review получают
его независимо. Во всех трёх запросах каждого проекта одинаковые полные тексты
выбранных файлов. Адресный review проверяет заранее выбранные `purpose` и
`data_flow.0`. Ожидаемые ответы в запросы не включались.

Полный review использует рабочую инструкцию и валидатор COS, но поиск отключён,
а контекст заменён общим пакетом. Это сравнение финального review при заданных
исходниках, **не** обычного маршрута от самостоятельного поиска до результата.
Два знакомых проекта, один ответ каждого вида, оценка ассистентом по исходникам:
это не независимая оценка обобщения. Отдельно два провайдера получили одну и ту
же старую задачу проверки гарантии Replay.

## Измеренный результат

| Проект | Простой ответ | Ответ + полный review | Ответ + адресный review |
| --- | ---: | ---: | ---: |
| Replay | 8 696 | 23 760 | 16 883 |
| Inspect | 6 863 | 18 992 | 13 034 |

Числа — reported input+output tokens всего соответствующего пути. Общий расход
серии **57 110**, поскольку общий черновик каждого проекта генерировался один
раз. Восемь обращений, один DeepSeek cache hit. Резерв до запуска 798 472,
лимит строго ниже миллиона. У GigaChat шлюз сообщил нулевой расход при ответе
за 24 секунды; это не доказательство бесплатного вызова. Стоимость по счёту
и расход сессии ассистента здесь не измерены. Повторов и fallback не было.

Replay: все три текста сохраняют повторный baseline-прогон и больше не заявляют
безусловную неизменность репозитория. Но называют профиль опциональным без
условия его обязательной валидности для квалификации; ошибочно объявляют полный
процесс создания профиля неизвестным, хотя функция видна целиком. Пропущено
условие равенства коллекций тестов. Полный review дополнительно удалил описание
диагностических проверок исходного репозитория. Адресный не изменил текст.
Ни один вариант не принят как полноценное описание по исходному критерию.

Inspect: полезное описание четырёх API, CLI, ограничений путей и эвристик.
Числовые значения по умолчанию и признак усечения не раскрыты. Полный review
верно заметил, что stderr/exit code относятся к CLI, а API выбрасывает исключения,
но удалил весь сценарий вместо уточнения области. Адресный снова оставил текст
без изменений. Оговорка об отсутствии тела `extract_python_structure` оправдана.

Отдельная гарантия Replay: кешированный DeepSeek снова подтвердил ложное
утверждение. GigaChat не прошёл проверку буквальности цитаты: добавил backticks
и заменил вызов на `result = _run_candidate(...)`. Его сырой ответ тоже поддержал
гарантию. Успешной альтернативы нет; по одному невалидному ответу нельзя оценить
общее качество модели или обосновать переключение провайдера.

## Решение и дальнейшая работа

Заранее заданное правило выбора не выполнено: простой путь не лучше по всем
критериям обоих проектов, полного принятого Replay нет. Default оставлен прежним.
Этот опыт не измеряет пользу `return_flags` отдельно и не оправдывает его
автоматическое удаление. Экспериментальный mechanism review остаётся opt-in.

Прежние рекомендации немедленно строить анализ всех возвратов заменены:
`project-description-evaluation` остаётся открытой, но с приоритетом 3.
Возвращаться к ней следует при измеренном блокере реальной задачи, с одной
гипотезой, исходным сравнением и заранее заданным условием остановки. Не добавлять
схему или слой после отрицательного опыта без такого обоснования.

Следующий пакет направлен на `development-pilot-next-case`:

1. Проверить актуальность источников, окружения и failing nodeids Toml-sort.
2. Доставить имеющиеся native observations и прежний отрицательный comparison
   в один ограниченный repair request; сохранить nomination `write_header_comment`.
3. Проверить патч на исходном дефекте, всех native tests и сохранении header/footer.
4. Получить final Reviewer и классифицировать результат, включая ручные вмешательства.
5. По факту выбрать перенос либо один конкретный блокер первых трёх ролей;
   новая инфраструктура требует связи с этим блокером.

Это следующий эксперимент, ещё не выполненный ремонт. В текущем этапе проверены
хеши десяти его сохранённых receipts: совпадают. Это только целостность evidence,
не свежий preflight исходников/окружения. Не подменять один model request несколькими
транспортными повторами; заранее записать общий бюджет и предел transports.
