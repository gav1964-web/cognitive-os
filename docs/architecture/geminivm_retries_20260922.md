# GeminiVM: три попытки при потере страницы ответа

22 сентября2026. Владелец явно разрешил повторять отправленный запрос при
возврате на пустую страницу и уточнил владельца механизма: GeminiVM.
Это новая политика восстановления; прежний запрет повторной отправки
из отчёта `geminivm_notice_20260922.md` описывает предыдущую реализацию.

GeminiVM выполняет максимум3 отправки в рамках одного CLI/API-запроса:
первоначальную и до двух повторных. Общая desktop lock удерживается на всём
цикле. Текст и выбранный маршрут модели не меняются; каждый повтор проходит
обычные проверки URL, калибровки модели и readback введённого запроса.
Шлюз5 и COS не получают новой логики повторов.

Условие повтора: наблюдалась генерация, после неё распознана READY — известная
пустая главная страница. Требуются последовательные READY-кадры
(`transitional_frames`, сейчас4) и минимум `empty_page_grace` секунд (сейчас3)
с первого такого кадра. Другой кадр сбрасывает подтверждение. Непосредственно
перед повтором вновь проверяются READY, URL Gemini и READY.

UNKNOWN, форма с оставшимся текстом, потеря фокуса, login, отказ модели,
ошибка копирования и обычный timeout генерации не запускают этот повтор.
Существующий повтор при явном service_error имеет свой прежний лимит и входит
в общий `max_attempts`; вложенного умножения числа отправок нет. В текущей
машинной конфигурации service_error_retries=0, это значение сохранено.

После трёх потерь контекста API GeminiVM возвращает HTTP503,
`error.code=response_context_lost`, `geminivm.retry_count=2`, общий run_id.
Успешная вторая/третья отправка возвращает обычный ответ с тем же счётчиком.
Каждая потеря сохраняет `attempt-N.json`, кадры и событие automatic_retry.
У шлюза5 новый код может нормализоваться в provider_error; retry_count/run_id
проходят существующий контракт. Установление причины сброса остаётся отдельной
задачей; этот механизм не доказывает её устранение или рост качества ролей.

Настройки: max_attempts по умолчанию3, диапазон1–3 (1 отключает повторы);
empty_page_grace по умолчанию3 секунды. response_timeout остаётся ограничением
одной попытки. Внешний HTTP-клиент должен дождаться суммарного цикла;
транспортные таймауты шлюза/COS в этом изменении не менялись.

Проверено338 тестами GeminiVM, включая успешную2-ю/3-ю отправку, три потери через
реальный HTTP handler с моделируемым X11, неизменность prompt, общий лимит
service_error/empty_page, короткие и прерывистые READY, смену страницы при
перепроверке и отсутствие повторов по другим отказам. Реальные генерации в этом
этапе не запускались. Установленные hashes совпадают; изменённые Python-модули
не превышают314 строк. Сервис8002 перезапущен, список моделей проверен.

`verification.json`, `focused.log` (61), `tests.xml`/`tests.log` (338), `restart.log`.
Изменения принадлежат `F:/ubuntu/test/GeminiVM`: core.py, config.py, state.py,
