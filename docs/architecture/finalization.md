# Завершение этапа разработки

В черновике можно временно превысить 400 строк. На границе завершённого этапа,
перед коммитом и в CI предел остаётся обязательным. Подсистема принадлежит Roles;
самостоятельного пакета и нового Git-репозитория нет.

```bash
python tools/finalize_stage.py --phase development
python tools/finalize_stage.py --repair --apply --test-target tests --pytest-plugin pytest_asyncio.plugin
python tools/canonical_verify.py --root . --write
```

Для небольшого изменения указывайте соответствующую группу regression tests.
`--test-target` и `--pytest-plugin` допускают повторение. Команда без `--repair`
работает без LLM и сторонних зависимостей; финальное превышение даёт ненулевой код.
`--repair` без `--apply` оставляет проверенную правку в отдельной копии, исходный
этап остаётся незавершённым. Если превышений нет, LLM и тесты повторно не запускаются:
это завершение проверки размера, не свидетельство прохождения остальных проверок.

Порядок работы:

1. `runtime/stage_finalization.py` использует тот же набор исходников, что repo lint.
2. `runtime/source_refactor_analysis.py` выделяет top-level функции без зависимостей
   от глобальных имён исходного модуля. До трёх проблемных модулей на один запуск.
3. В отдельной копии выполняются исходные тесты; пустая коллекция и падения закрывают допуск.
4. `runtime/source_refactor_planner.py` вызывает настроенный L4.5 через существующий
   `local_inference`. Модель предлагает только группы функций, имена новых модулей
   и обоснование. Ответ привязан к хешу исходника; код и команды от модели не принимаются.
5. `runtime/source_refactor_patch.py` переносит исходный текст функций, сохраняет
   импорты по прежнему пути и `__module__`, наследует владение в карте подсистем.
6. `runtime/stage_finalization_verification.py` повторяет те же тесты и проверяет
   границы, сравнивает коллекцию и количество успешных тестов. Проверяется,
   что тесты не изменили снимок исходников; размер отдельно проверяет final audit.
7. `runtime/stage_finalization_workspace.py` сверяет актуальность всего снимка и
   применяет проверенные файлы; частичное применение откатывается при ошибке.

Функция переносится целиком: изменения сигнатуры, тела, декораторов и тестов
не входят в данный оператор. Не поддерживаются классы, вложенные/async/generator
функции, декораторы, глобальные зависимости, динамическое исследование namespace,
неподдерживаемые аннотации и defaults. Один слишком большой function body требует
отдельного рефакторинга. Новый модуль не должен затенять stdlib или существующий
модуль/пакет. Сохранение физических путей к коду и `function.__globals__` не обещается;
это узкий контракт переноса с проверкой выбранного regression scope, не доказательство
полной семантической эквивалентности Python-программ.

Снимки ограничены 10 000 файлами и 100 MB. Исключаются артефакты, external corpus,
виртуальные окружения, `.git`, `.env*` и машинный `config.json`. Symlink-пути
не переносятся. Это изоляция рабочих копий, а не отдельная ОС или сетевой sandbox.
LLM получает только ограниченный контекст кандидатов; ключ API не пишется в receipt.
Бюджет вывода плана — 2400 токенов. Усечённый ответ отклоняется; автоматического
перехода на другую модель и бесконечных повторов нет.

Результаты: `completed`, `verified_patch`, `needs_refactoring`, `needs_replanning`.
`source_applied` явно показывает применение. `original_source_unchanged` в checks
относится к проверке перед применением; после успешного применения изменение ожидается.
Причина остановки, diff, JUnit, перечень файлов и телеметрия сохраняются в
`artifacts/stage_finalization/stage-*/`. Финальный audit также входит в canonical/CI.

CLI после завершения вызова обновляет постоянную очередь `DEVELOPMENT_TASKS.json`,
в том числе при остановке до создания snapshot. Она содержит следующий шаг для
ассистента и доступна через `tools/project_context.py`; порядок работы описан в
[DEVELOPMENT_TASKS.md](../../DEVELOPMENT_TASKS.md). API и синтетический пилот не
пишут очередь. `--phase development` не регистрирует промежуточные превышения;
`--no-handoff` предназначен для отдельных аудитов без записи. Ошибка сохранения
очереди даёт ненулевой exit code. При устранённом размере, но незакрытых ручных
задачах CLI возвращает `needs_handoff_review`: нужны regression review и receipt.
Очередь не означает запуск агента в фоне и не расширяет область разрешённых работ.

Пилот:

```bash
python tools/evaluate_stage_finalization.py --cases 24
```

Это синтетическая калибровка: 18 вариантов импортов, аннотаций, API и зависимостей
и шесть неподдерживаемых структур. Она проверяет интеграцию с реальной LLM и
остановку за пределами оператора. Повторяющиеся семейства функций не считаются
независимым production benchmark. Receipt фиксирует идентификатор модели из ответа
шлюза, сообщённые токены, время и исход каждого случая. Нулевые токены ответа шлюза
не доказывают отсутствие вычислений или расходов. Цена в USD остаётся неизвестной
до настройки тарифа шлюза.

Калибровка 10 сентября: в первом прогоне **12/18** поддерживаемых задач прошли
полный цикл с применением; **6/6** неподдерживаемых структур остановлены корректно.
Выборочный повтор дал ещё одно исправление — **13/18** суммарно; в остальных пяти
повторных попытках шлюз вернул HTTP 500. Это ограничение доступности маршрута,
а не измеренная ошибка плана. Поздний диагностический запрос одного из этих случаев
получил ответ, но не применялся и не засчитан исправлением. Результаты первого
прогона сохранены отдельно от повторов: [receipt](finalization_pilot_20260910.json).
Старый alias не доказывает конкретную версию весов модели за шлюзом.
