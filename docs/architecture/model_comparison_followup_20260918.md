## Почему ремонт не сработал

У всех трёх новых repair-маршрутов сообщения побайтово совпали с прежним direct
запросом. В них уже были интерфейсы tuple, тест, наблюдения и прежние неудачи.
Native baseline и SHA-привязки проверены перед каждым вызовом.

- v3.2 добавила `if not items and not footer_comment`, хотя наблюдения показывают
  непустой footer_comment на падающем входе. Новая ветка не исправляет этот путь.
- Qwen Plus проверила `isinstance(original.body[0], Comment)`, хотя элемент body
  является парой `(key, item)`. Новая ветка также не обрабатывает нужный случай.
- Оба кандидата проверены полной native-регрессией; восемь режимных выходов
  совпали с исходной версией. Корпус не изменён, финальный Reviewer не достигнут.
- GLM вернула пустой текст: usage3500 output tokens, а точная запись кеша пуста.
  Это отказ получения кандидата в данном режиме, не доказательство плохого кода.

Подтверждённый разрыв — использование уже видимых фактов при построении кандидата.
Прямая модельная ветка не даёт независимо приписать провал Analyzer, Architect или
SpecWriter. Оснований добавлять ещё контекст или специальное правило для Toml-sort
по этому результату нет. Предыдущая ошибка передачи контекста уже устранена.

## Проверка полного текста

Четыре модели получили одинаковые полные источники и одинаковые сообщения.
JSON пользовательского сообщения переформатирован одинаково для обхода прежнего
кеша; разобранные данные и системная инструкция сохранены. Все четыре ответа
имели cache_hit=false и актуальные source hashes. Адресные предварительные notes
остались явно недоверенными и противоречивыми: сравнение проверяет также способность
перепроверить их по источникам. Это известный development-кейс, не blind holdout.

Главный критерий — явно объяснить, что optional-сигнатура environment_profile
не означает достижимость qualified без валидного профиля — ни один текст полноценно
не выполнил. GLM сохранила больше деталей, но объявила диагностические флаги
подтверждением неизменности и обобщила таймауты всех фаз до environment_blocked.
Фактически ошибки fixed-прогона участвуют в oracle_fix_not_verified.

Последний слот использован для общей проверки текста GLM: проследить defaults,
обработчики, итоговые статусы и различить диагностические флаги и гарантии.
Неверные предварительные notes заменены реальным черновиком; правильные ответы
и проектные исключения в prompt не добавлялись. Это сравнение процесса, а не
изолированная смена модели. За75,5с получен пустой final content при4096 output
tokens; новой исправленной версии нет. Дополнительных повторов не было.

Точный read-only поиск в кеше подтвердил также пустой content у R1 на первом
наборе при4096 output tokens. Причина на стороне backend, включая возможные
reasoning tokens, независимо не установлена. Повышать вывод о качестве модели
из одной пустой выдачи нельзя; текущий gateway ограничивает max_tokens4096.

## Пять работ и границы результата

1. Выполнено сравнение явно выбранных моделей на замороженном repair-запросе;
   native-кандидаты проверены, ни один не принят.
2. Локализован разрыв evidence→candidate: неправильная ветка и неправильный тип,
   несмотря на видимый контекст. Непринятый код не был исправлен ассистентом и
   засчитан как успех COS. Детерминированные проверки правильно отклонили его.
3. В предыдущем этапе реализован plugin0.16.0: ограниченный try/except/else/finally
   в существующем анализе свойств. Правила остаются в плагине; shared core нейтрален.
4. Свежие авторские контрасты и противоположные случаи проверены с CPython;
   все13 моделей прошли общий компактный набор, четыре — полный текст. Общий перенос
   на независимые проекты и исправление всех ошибок описания не подтверждены.
5. Учёт unknown сохранён, результаты и план актуализированы. Default прежний;
   новый режим проверки текста не допущен в основной маршрут.
