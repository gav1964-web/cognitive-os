# GeminiVM: явный контракт ответа после восстановления

23 сентября 2026. Продолжение исправления приоритета запросов.

В предыдущем прогоне Gemini после service_error и одного `?` вернула приветствие.
Чат был прежним и ответ новым, но провайдер объявил его normal; лишь JSON-парсер
COS остановил обработку. Совпадение чата не означает выполнения исходной задачи.

## Контракт и границы

GeminiVM принимает явный `response_format: {"type": "json_object"}` через HTTP
и `response_format="json_object"` через Python API. Это проверка готового ответа
в провайдере, не управляемый JSON-режим генерации Gemini Web.

Допускается ровно один JSON-объект, в том числе один целый блок Markdown JSON:
снимается только внешнее ограждение и пробелы; внутренние JSON-байты и значения
сохраняются. Произвольное извлечение объекта из поясняющего текста запрещено.
Несколько объектов, повторяющиеся ключи, NaN/Infinity, массивы и неоднозначный
режим сравнения отклоняются. Исходный ответ остаётся в attempt-артефакте;
response-contract.json фиксирует результат, нормализацию и SHA256.

При нарушении возвращается HTTP422 `invalid_response_format`. Шлюз5 сохраняет
этот код и диагностику; COS сохраняет причину и останавливает запрос. Новых
повторов или оснований автоматического fallback не добавлено. Исходные refusal,
service_error, timeout не подменяются ошибкой формата. Без явного контракта
обычные разговорные ответы, включая приветствия, сохраняют прежнее поведение.

Continuation accepted теперь явно означает `ui_response_identity`.
Даже при правильном JSON `task_correctness=not_evaluated`: схема роли,
доказательства, исходный код и native-тесты по-прежнему нужны для приёмки задачи.
Например, JSON с бессодержательным ответом пройдёт проверку формата; это не
универсальная проверка смысла и не исправление внутренних ошибок Gemini.

## Проверки

455 тестов GeminiVM прошли. После добавления response_format в журнал запроса
повторён соответствующий набор проверки контрактов, восстановления и deadline.
22 теста шлюза проверяют новый контракт и прежние маршруты/ошибки.
Два сквозных офлайн-теста используют настоящий код COS, HTTP-шлюз, SDK и
GeminiVM HTTP/core; только сеть и экран заменены контролируемыми границами:
сохранённое приветствие →422, один JSON-блок →принятый объект. Каждый сценарий
делает один HTTP-вызов в изолированном контуре и две имитации отправки
(исходный запрос и штатный `?`). Внешних запросов к модели нет.

Первоначальные ошибки изолированной проверки шлюза были связаны с отсутствием
конфигурационных фикстур; перенесены только алиасы/маршруты/список моделей,
без ключей и endpoints. Сквозной тест сначала запускался в окружении без Pillow,
затем с неверным именем модели тестового провайдера; исправлена настройка теста.
Эти неудачи сохранены в промежуточных XML, итоговые проверки указаны отдельно.

Установка проверяет хеши изменяемых файлов, сохраняет резервные копии, допускает
перезапуск HTTP-сервисов только при свободном desktop и отсутствии текущих
HTTP-соединений. Firefox и VM не перезапускаются. Итог установки и активации
JSON-контракта первых трёх ролей отражён в DEVELOPMENT_STATUS.

## Задержка интерфейса

Разбор сохранённого run `20260923T064154-a7cf0e4aefde` обнаружил57 SSH-вызовов
до первой отправки:19 отдельных проверок фокуса заняли18,187с, остальные38 —
39,889с. Это длительности SSH-операций, не чистая сетевая задержка и не обещание
экономии18с. Общая подготовка ранее занимала82,491с вместе с ожиданием блокировки.

Следующий ограниченный шаг — объединить проверку фокуса и соответствующий
key/click в одну удалённую операцию. Проверка должна оставаться свежей перед
каждым действием; sleeps, clipboard readback, привязка ответа и deadline
сохраняются. До включения нужны отрицательные проверки потери фокуса между
действиями. Код ускорения в этом этапе не менялся, измеренного ускорения нет.
