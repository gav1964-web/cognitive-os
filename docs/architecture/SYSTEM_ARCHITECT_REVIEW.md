# Cognitive OS — документ для архитектурного ревью

**Срез на 29 сентября 2026 · Версия 1.0**

Аудитория: системный архитектор, технический руководитель, инженер платформы.
Документ описывает существующую систему, принятую целевую архитектуру и вопросы,
по которым требуется внешняя оценка. Это обзор для обсуждения, а не заключение
о готовности к промышленной эксплуатации. Части реализации находятся в рабочем
дереве и ещё не зафиксированы отдельным релизом.

## 1. Назначение и основная гипотеза

Cognitive OS (COS) — исследовательская программная платформа для выполнения
инженерных задач над программными проектами. Она связывает анализ исходников,
архитектурное решение, проверяемую спецификацию, подготовку изменения, исполнение
тестов и решение о приёмке. Название OS обозначает организацию этих механизмов;
это прикладная система, работающая поверх обычной операционной системы.

Пользователь задаёт цель и допустимые границы действий. Результат — артефакты
анализа и решения, кандидат изменения, свидетельства проверок и явно обозначенный
статус: принят, отклонён, требует данных или остановлен ограничением.
Работающий кандидат и его установка в исходный проект — отдельные действия.

**Исследовательская гипотеза:** повторяемые решения с известной областью
применимости можно переносить из LLM в проверяемые механизмы. Накопленный опыт
должен обобщаться в компетенции для классов задач. LLM остаётся средством работы
с неопределённостью и подготовки новых решений. Ожидаемый эффект — снижение
стоимости и задержки при сохранении качества; универсальность и экономический
эффект этого подхода пока не доказаны.

Основные сценарии:

- объяснение назначения и устройства существующего проекта с опорой на исходники;
- подготовка и проверка ограниченного изменения в существующем проекте;
- воспроизведение дефекта и проверка исправления в отдельной копии;
- развитие компетенций через исследование случаев и проверяемый допуск;
- обращение за внешней помощью при поддержанном сбое самой COS с продолжением
  задания после проверки патча.

Работа с существующими Python-проектами проверена существенно глубже произвольной
разработки с нуля и других языков. Поддержка конкретного сценария не означает
способность самостоятельно развивать любой репозиторий.

## 2. Текущее положение

| Область | Что существует | Граница подтверждения |
|---|---|---|
| Анализ → архитектура → спецификация | Ролевые артефакты, ограниченный контекст исходников, проверки связности и области задачи | Качество зависит от задачи, модели и достаточности свидетельств |
| Изменение проекта | Подготовка кода и тестов, выполнение в копии, review и дополнительные проверки | Не все задания завершаются без доработки COS извне |
| Плагины компетенций | Отдельные владельцы алгоритмов и локальных KB, реестр и проверка контрактов | Миграция прежних предметных знаний не завершена |
| Inspect и Replay | Два выделенных устанавливаемых Python-пакета | Остальная система остаётся теснее связанной |
| Исполнение и восстановление | Pipeline, файловая очередь, leases, журнал, отдельные процессы | Распределённая отказоустойчивость и нагрузочные SLO не подтверждены |
| Внешний ремонт COS | Аутентифицированный файловый протокол, локальная policy, проверка и переключение выпуска | Поддерживаются ограниченные патчи и конкретная граница checkpoint |
| Windows worker | Установленная служба, отдельный runtime/SID, проверенные ACL и живое продолжение | SCM stop/restart во время активной работы остаётся отдельной проверкой |

Последний опыт на пяти задачах дал **1/5 завершений в первом прогоне без
вмешательства и 4/5 закрытых задач после общих исправлений COS**. Пятый кандидат
прошёл отдельные поведенческие проверки, но весь процесс его приёмки не завершён.
Это работающий инженерный прототип с частичной автономностью.

## 3. Контекст системы и размещение

```text
Пользователь / оператор
        │ цель, допустимые действия, бюджет
        ▼
COS: роли, политики, контракты, контроллер
        ├── чтение ──► исходный проект
        ├── выполнение ──► рабочие копии / worker ──► тестовые процессы
        ├── артефакты ──► журнал, checkpoint, отчёты, учёт расхода
        ├── запросы ──► локальный шлюз «5» ──► провайдеры LLM
        └── инцидент ⇄ файловый обмен ⇄ внешний помощник

Проверенный кандидат ──► отдельный допуск установки ──► целевой проект
```

Базовая реализация — Python, файловые JSON-контракты и артефакты, Git и pytest
для значительной части проверок. CLI-инструменты организуют сценарии. Два пакета
подключаются через обычную установку; в разработке используются editable installs.
Файловое состояние позволяет сохранять промежуточные результаты и разбирать
причины отказа, но требует явных правил блокировки, атомарности и восстановления.

Шлюз «5» — отдельный проект и самостоятельная граница эксплуатации. Текущий
локальный маршрут стенда — `http://127.0.0.1:8200/v1`. COS проверяет готовность
шлюза и при необходимости запускает разрешённый launcher до начала учёта inference.
Название роли не закрепляет её за конкретной моделью.

В последних ролевых опытах использовалась Luna. В документах сохранены более
ранние маршруты DeepSeek, GigaChat и GeminiVM; они не должны восприниматься как
одновременно действующая рекомендуемая конфигурация. GeminiVM — отдельный
провайдер доступа через веб-интерфейс, не обязательная часть архитектуры COS.
Перед эксплуатацией требуется зафиксировать единую матрицу актуальных маршрутов.

## 4. Логическая декомпозиция

| Подсистема | Ответственность и основные выходы | Точки входа |
|---|---|---|
| Inspect | Структура проекта, стек, Python-символы, команды; факты для анализа | `packages/cognitive-inspect/src/cognitive_inspect/` |
| Roles | Ролевые переходы, анализ, ADR, спецификации, планы, подготовка и review изменений | `runtime/configured_role_pipeline.py`, `runtime/feature_quality.py` |
| Execution | Исполнение capability/pipeline, очередь, worker, восстановление | `runtime/executor.py`, `runtime/async_executor.py`, `runtime/durable_queue.py` |
| Replay | Воспроизведение baseline, запуск тестов, проверка кандидата и среды | `packages/cognitive-replay/src/cognitive_replay/`, `runtime/native_failure_acceptance.py` |
| Evidence | Схемы, идентичность и происхождение артефактов, связывание результатов | `runtime/evidence_ledger.py`, `runtime/schema.py` |
| Research | Корпус случаев, получение кандидатов знаний, разделение обучения и оценки | `runtime/local_historical_defect_mining.py`, `runtime/three_route_evaluation.py` |

Это смысловые границы, не шесть микросервисов. Inspect и Replay имеют собственные
API, зависимости и тесты; они не импортируют runtime COS и друг друга. Роли и
Execution используют их. Границы остальных областей описаны, но не равнозначны
независимым deployment units. В legacy native-failure intake сохраняется связность,
из-за которой его полное выделение отложено.

Отдельно расположен контур внешней помощи: протокол, контроллер выпуска,
локальная policy, worker и адаптер продолжения роли. Его задача — контролируемо
изменять поддержанную часть COS, сохраняя независимую точку приёмки.

## 5. Роли и контракты результата

В системе несколько маршрутов выполнения; они используют общие контракты,
но не сведены к одному универсальному циклу. Конфигурируемый ролевой workflow,
цикл разработки feature и native-repair trial следует различать при ревью.

| Роль | Основная ответственность | Артефакт / критерий |
|---|---|---|
| Analyzer | Установить факты, назначение, границы и недостающие данные проекта | `ProjectMapReport`, `ScopeSelectionReport`; ссылки на выбранные исходники |
| Architect | Предложить дизайн и ограниченный первый участок изменения | `ArchitectureDecisionRecord`; связь цели, решения и затрагиваемых компонентов |
| SpecWriter | Превратить решение в исполнимые требования и проверки | `TechnicalSpec`; приёмочные случаи и сохранение прежнего поведения |
| Implementer / Programmer | Подготовить план или код в рамках выбранного маршрута | `ImplementationPlan`, `PatchPackage` либо кандидат feature |
| Tester / тестовый контур | Выполнить проверки и сохранить фактический результат | `TestPlan`, `TestResult`, native-отчёты |
| Reviewer / Challenger | Проверить соответствие, выявить пробелы и контрпримеры | Review, причина отказа, возврат ответственному этапу |
| Researcher | Получить дополнительные сведения в разрешённых пределах | `EvidenceCandidate`, `KnowledgeGapPacket` |

Analyzer не получает право менять исходный проект. ADR не является разрешением
исполнить произвольный код. Успешный ответ модели и корректная JSON-схема не
равнозначны поведенческой корректности. Переходы связываются с целью, областью
работы, версиями/хешами исходников и артефактами предыдущего этапа.

## 6. Типовой цикл изменения проекта

1. **Зафиксировать вход.** Цель, выбранные файлы, область изменения, окружение,
   разрешения, бюджет и исходные хеши. Недостаточный контекст явно ограничивает вывод.
2. **Проанализировать и спроектировать.** Сформировать факты, ADR и спецификацию.
   README служит одним из свидетельств; утверждения о поведении требуют сверки
   с кодом и проверками. Неисполнявшееся поведение не выдаётся за наблюдение.
3. **Проверить спецификацию.** Убедиться в исполнимости приёмки и сохранении
   нужного прежнего поведения. Неоднозначность возвращается владельцу требования.
4. **Подготовить кандидата.** COS пишет изменение в отдельной рабочей копии.
   Изменение исходного проекта во время цикла обнаруживается проверкой хешей.
5. **Выполнить проверки.** Baseline/candidate, выбранная регрессия, review;
   в экспериментах — также заранее зафиксированная внешняя приёмка.
6. **Обработать отказ.** Вернуть его подходящей роли с ограниченным числом циклов.
   Контрпример должен сохраняться как проверяемое обязательство, а не исчезать
   после следующей генерации.
7. **Выдать результат.** Отдельный кандидат и отчёт либо checkpoint с причиной
   остановки. Установка требует соответствующего допуска; откат восстанавливает
   файлы конкретной установки, но не отменяет внешние эффекты выполненного кода.

В native-repair маршруте до модельного предложения проверяется воспроизводимость
исходного отказа. Пустой/неполный JUnit, таймаут или изменившиеся исходники не могут
подтвердить успешность исправления. Поддержанная точка продолжения перепроверяется;
произвольная миграция любого состояния после изменения COS не реализована.

## 7. Компетенции, знания и место LLM

Принятое направление: **один явный владелец предметного знания — плагин
компетенции**. В нём совместно развиваются алгоритм, локальная KB, применимость,
контракты, тесты и evidence. Единица выделения — механизм для класса задач,
а не каждый отдельный факт. Другой плагин обращается через версионированный API.

Общее ядро отвечает за вызов, выбор по метаданным, проверку контрактов и
разрешение неоднозначности. Оно не должно обрастать специальными ветками по
предметным компетенциям. Общий каталог, контекст задачи и журнал свидетельств
остаются инфраструктурой. Плагин может использовать декларативную KB или обычный
алгоритм: универсальный интерпретатор не обязан выражать любую предметную процедуру.

Реализованные примеры владельцев: exception pickle, append mapping, JSON
serialization, JSON parsing, text splitting, описание проекта. Для knowledge
provider проверяются lifecycle, схемы, происхождение импорта и code/KB hashes.
Предложение патча не наделяет его владельца правом применения.

Желаемый цикл накопления: случай → кандидат механизма → область применимости →
контрастные проверки → допуск → наблюдение дальнейшего применения. Части этого
цикла существуют, но автономное обобщение произвольного опыта в новую надёжную
компетенцию не подтверждено. Неизвестный случай должен приводить к уточнению,
разрешённому LLM-вызову или остановке.

Критерий успеха здесь — качество, стоимость и задержка **всего задания**, включая
отказы и повторные проверки. Количество плагинов или сокращение одного запроса
не являются самостоятельными показателями улучшения.

## 8. Контролируемый ремонт самой COS

Контур рассчитан на ситуацию, когда помощник не имеет прямого доступа к COS.
Выбран файловый обмен через контролируемое хранилище; конкретный внешний сервис
не подключён, SMTP не требуется.

```text
COS / контроллер                 Файловый обмен              Помощник
       │ инцидент + контекст ───────────────────────────────────► │
       │ ◄────────────────────── запрос контекста / патч ──────── │
       │ проверка конверта и локальной policy                     │
       │ воспроизведение baseline → проверка кандидата            │
       │ переключение выпуска → resume новым процессом            │
       │ результат / следующий ограниченный инцидент ────────────►│
```

Конверт `cos.remote_support.v1` использует HMAC-SHA256. Локальная неизменяемая
policy задаёт экспортируемые и редактируемые файлы, команды проверок, checkpoint,
срок действия и лимиты. Команды передаются как argv без shell. Повторная доставка
обрабатывается по сохранённой квитанции. Неизвестный сбой не превращается
автоматически в разрешение ремонта: поддержанный trigger должен совпасть.

После успешных проверок контроллер переключает указатель выпуска и запускает
resume в новом процессе. При отказе возвращает baseline pointer. После прерывания
с неизвестными последствиями нужна сверка состояния; задача не повторяется вслепую.

Ограничения v1: существующие разрешённые Python-файлы, до 400 строк; без новых
production-файлов, удаления, изменения тестов, обновления контроллера и общей
миграции checkpoint. Ролевой адаптер проверен на границе принятой спецификации
до попыток Programmer. Контроллер остаётся точкой контроля вне такого патча.

## 9. Доверие, изоляция и целостность

| Граница | Действующий механизм | Что он не гарантирует |
|---|---|---|
| Модель → COS | Разбор полного JSON, schema, scope и consumer-проверки | Истинность вывода и достаточность тестов |
| Исходники → evidence | Хеши, пути, происхождение, привязка к контексту | Что ссылка действительно доказывает всю заявленную семантику |
| Плагин → runtime | Registry/lifecycle/contracts, проверка происхождения; восстановление импортов | Изоляцию произвольного доверенного Python-кода от всего хоста |
| Кандидат → исполнение | Отдельные копии и процессы; локальный worker с SID/ACL | Полноценную песочницу для враждебного кода |
| Помощник → контроллер | MAC, incident/policy/baseline binding, локальная приёмка | Шифрование и неоспоримое авторство между владельцами общего ключа |
| Выпуск → задача | Проверка checkpoint и запуск новым процессом | Автоматическую отмену сетевых и иных внешних эффектов |

Файлы проекта и текстовые ответы — данные с ограниченным доверием. Для передачи
внешней модели нужны разрешённый состав контекста и подходящий режим доступа.
Фильтр имён файлов не обнаруживает любой секрет внутри исходника или журнала.
Комплексная защита от prompt injection и исполнение враждебного кода в строгой
изоляции не должны считаться доказанными свойствами текущего прототипа.

Недавний дефект показал значимость границы процесса: sync/async executor оставлял
`sys.path` и `plugins.*` связанными с временным workspace. Исправление сохраняет
состояние плагинов внутри pipeline и восстанавливает импорты хоста после вызова.
Прямые вызовы сериализуются общей блокировкой импортов; для параллельной изоляции
используются процессы. Последствия для пропускной способности ещё нужно измерить.

## 10. Состояние, восстановление и стоимость

Ролевые артефакты, отчёты, checkpoint, состояние файловой очереди и inference
ledger имеют разные назначения и не должны заменять друг друга. История отказов
сохраняется рядом с успешным результатом. Версия кода, входов и policy определяет,
какие результаты допустимо повторно использовать.

Перед платным обращением резервируется допустимый расход. Сообщённый provider usage
сохраняется и при ошибке; неизвестный расход учитывается резервом, а не нулём.
Контроллер резервирует allowance перед запуском worker и сверяет durable ledger
после завершения. Авария контроллера не освобождает невыясненный расход.

История кэша подтверждает уже учтённый запрос только при точном совпадении
содержимого, модели, параметров и ответа. Она не заменяет ролевое решение.
Этот учёт относится к вызовам COS; он не измеряет расход сессии внешнего помощника.
Сопоставимость токенов между провайдерами и денежная стоимость требуют отдельной
тарифной модели. Токены сами по себе не являются полным показателем стоимости.

В пакете пяти задач потрачено **1 591 884 токена**, unknown 0; **74,8%** пришлись
на SpecWriter и аудит. Пятая задача остановилась, когда следующий запрос с
резервом не помещался в лимит. Это одновременно подтверждение работы бюджетного
ограничения и свидетельство высокой стоимости доведения спецификации до приёмки.

## 11. Доказательства и оценка зрелости

| Наблюдение | Результат | Как интерпретировать |
|---|---|---|
| Три задачи на модулях шлюза 5, map и VR | 3 завершения; 46 собственных и 73 внешних проверок | После инженерных доработок COS; не три успеха без вмешательства |
| Локальная оценка итоговых артефактов тех трёх задач | Analyzer 9.67; Architect 9.83; SpecWriter 9.50 | Оценка ассистента малой выборки, не независимая сертификация |
| Следующий пакет пяти задач | 1/5 с первого прогона без вмешательства; 4/5 закрыто после доработок | Главный текущий показатель ограниченной автономности |
| Установка и откат в копии полного VR | 14 тестов и 41 вложенная проверка на 15 DWG | Оригинал не изменён; не полная проверка приложения/UI |
| Файловый ремонт | Контролируемый инцидент, проверка патча, resume; отдельный живой ролевой опыт | Механизм работает в проверенной конфигурации, не любой self-repair |
| Регрессия COS после расследования | Полный: 5140 passed, 5 failed, 6 skipped; все пять затем прошли в группе 30/30 и снимке | Совокупное подтверждение, не единый полный зелёный прогон |
| Пакеты / плагины | 60/60 и 237/237 | Соответствующие программные контракты; не измерение автономности |

Оценка автора документа: инфраструктура проверки, происхождения и контролируемого
выполнения развита лучше, чем устойчивость завершения произвольной задачи без
помощи. Первые три роли дают полезные результаты, но спецификация и аудит остаются
узким местом по стоимости и завершению цикла. Общий уровень 9.7+ не заявляется.

Изменяемый внешний curriculum также сохраняет отрицательный результат: для проекта
5 — 0.963 и `needs_improvement` из-за недостающей source evidence. Это другая шкала
и другой опыт; переводить её в балл роли или смешивать с таблицей выше нельзя.

## 12. Основные риски и инженерные решения

| Риск / компромисс | Текущее решение | Что требуется проверить дальше |
|---|---|---|
| Одни роли пишут и оценивают похожие решения | Независимые внешние проверки в опытах, сохранение контрпримеров | Качество на новых задачах без участия автора COS в уточнении решения |
| Аудит расширяет задачу бесконечно | Явная граница goal/scope, возврат ответственному этапу | Сохранение нужной полноты без навязывания соседних исправлений |
| Повторная генерация тратит основной бюджет | Checkpoint, ограниченные повторы, резерв до вызова | Сокращение повторного контекста и механический ремонт метаданных |
| Описанная архитектура расходится с кодом/config | Контракты, карта подсистем, source-bound evidence | Один актуальный манифест поддержанных маршрутов и возможностей |
| Рост связности многочисленных модулей | Владение компетенциями, локальный контекст, 400 строк на Python-файл | Граф зависимостей и цена изменения; длина файла не доказывает модульность |
| Локальная файловая модель усложняет масштабирование | Locks, leases, атомарные записи, журналы | Сценарии нескольких хостов, retention, backup/restore, нагрузочные пределы |
| Рабочая копия воспринимается как песочница | Отдельные права и процессы, явные ограничения допуска | Модель угроз и изоляция для выбранного класса недоверенного кода |
| Формальная корректность скрывает плохую семантику | Native acceptance, review, контрпримеры | Полнота oracle и обнаружение ошибок самого тестового замысла |

## 13. Предлагаемые приоритеты

Это рекомендации для архитектурного обсуждения, не утверждение о выполненных работах.

1. **Зафиксировать поддержанный продуктовый контур.** Один воспроизводимый сценарий
   от цели до принятого кандидата; явные входы, отказы, установка и ответственность.
   Закрыть оставшийся пятый цикл с сохранением истории, не меняя задним числом приёмку.
2. **Сократить стоимость SpecWriter и аудита.** Отделить механическое исправление
   метаданных от нового проектирования, повторно использовать проверенный контекст.
   Сравнивать полный расход и завершения на новой выборке, включая неудачи.
3. **Зафиксировать проверяемый релиз.** Полный зелёный прогон единого снимка, версии
   пакетов/config/routes, список поддержанных checkpoint, эксплуатационная инструкция.
4. **Завершить выбранную границу изоляции.** Определить модель угроз, проверить
   stop/restart при активной задаче, аварийный учёт, восстановление и внешние эффекты.
5. **Продолжать перенос компетенций по реальным границам.** Сначала контракт,
   потребители и regression evidence; отдельный сервис или пакет — когда нужна
   независимая эксплуатация либо доказана самостоятельность API.

## 14. Вопросы системному архитектору

- Достаточно ли чётко разделены предложение решения, допуск исполнения и приёмка?
  Какие компоненты должны входить в минимальную доверенную часть системы?
- Какой первый эксплуатационный профиль выбрать: локальный инженерный инструмент,
  выделенный worker для команды или многопользовательская платформа?
- Какие гарантии нужны для повторов, идемпотентности и восстановления внешних эффектов?
  Где файловой модели достаточно, а где потребуется транзакционное хранилище?
- Правильно ли выбрана единица компетенции? Как контролировать зависимости между
  плагинами, не возвращая предметные правила в общий маршрутизатор?
- Какие тесты достаточны для приёмки модельной спецификации, если сама модель
  может придумать неполный oracle? Кто владеет внешним критерием успеха?
- Где целесообразнее вкладываться сейчас: качество SpecWriter, сокращение
  повторного контекста, изоляция или унификация нескольких execution-маршрутов?
- Как измерять полезность детерминированных компетенций: доля задач, качество,
  задержка и денежная стоимость полного цикла с учётом отказов?

Ожидаемый результат ревью: список критических архитектурных замечаний, согласованная
граница первого поддержанного продукта и проверяемые условия перехода к эксплуатации.
