# GeminiVM: восстановление после внутренних ошибок Gemini

22 сентября2026. Владелец показал `I encountered an error doing what you asked.
Could you try again?` и явно поручил GeminiVM обрабатывать такую ошибку.
Точный текст уже распознавался как service_error. Причина отсутствия повтора
в предыдущем прогоне — service_error_retries=0 в рабочем provider.yaml.

Изменено внутри GeminiVM:

- service_error_retries по умолчанию2, допустимый диапазон0–2; в рабочей
  конфигурации0 заменён на2, остальные машинные настройки сохранены.
- Общий max_attempts=3 остаётся пределом первоначальной и всех повторных
  отправок. Service errors и подтверждённые пустые страницы расходуют его
  совместно, а не образуют вложенные циклы.
- Сохраняются одинаковые prompt/model, новый чат на повторе, проверки
  калибровки/readback и единая desktop lock. Каждая попытка остаётся в trace.
- После трёх внутренних ошибок GeminiVM возвращает HTTP502/service_error,
  retry_count2; текст ошибки теперь включает число попыток. Успех на2-й/3-й
  отправке возвращает обычный полезный ответ и фактический retry_count.
- Цитата ошибки внутри полезного ответа, отказ, suspected_stub, UNKNOWN,
  ошибка копирования и обычный timeout не приобретают новые повторы.

Классификатор не расширялся предположительными шаблонами: используется уже
проверенное полное короткое сообщение. Повторы не перенесены в шлюз5 или COS.
Параметры0/1 сохраняют возможность более строгого ограничения. Per-attempt
response_timeout не менялся; внешние таймауты могут ограничивать весь цикл.
Механизм восстанавливается после наблюдаемого отказа, но не устраняет внутреннюю
причину ошибки на стороне Gemini и не объясняет прежние сбросы страницы.

Полный набор GeminiVM:346 passed. Новые проверки используют точный текст
скриншота через настоящий HTTP handler с моделируемым X11: успех со2-й/3-й
отправки, три ошибки, смешанные service_error/empty_page в разных порядках,
предел2 при сниженном max_attempts, неизменность prompt и сохранение попыток.
Существующие проверки цитат/отказов и отключения повтора сохранены.
Изменённые Python-файлы≤315 строк, установленные hashes проверены.
Сервис8002 перезапущен, API списка моделей доступен.

Evidence: `artifacts/geminivm_service_retry_20260922/`: `before-hashes.json`,
`installed.json`, `verification.json`, `tests.xml`, `tests.log`, `restart.log`.
Машинная конфигурация в контекст не копировалась; installer проверяет hashes
и эквивалентность YAML за исключением единственного изменяемого значения.

Живая проверка оформлена отдельным лимитом: `live/protocol.json`, максимум1
HTTP-запрос и3 отправки внутри GeminiVM. Payload побайтно по списку сообщений
совпадает с прежним публичным humanize metric-кейсом; диагноз переиспользуется.
Ассистент не пишет кандидата за модель, исходный корпус остаётся неизменным,
unknown usage не заменяется нулём. Итог — в `live/summary.json`.

Живой результат:1 HTTP-вызов, ровно3 отправки, все три service_error.
Повторы начались автоматически в11:41:07 и11:42:44 UTC; окончательная ошибка
в11:44:19. Run `20260922T113912-db1d65064988`, цикл313.25с.
GeminiVM вернула `Gemini returned service_error after 3 submission attempt(s)`;
через шлюз в COS дошли service_error, retry_count2, run_id и модельPro.
COS остановилась контролируемо, без второго HTTP-вызова и без оценки качества.
Исходный корпус неизменен. Кандидат humanize не получен; внутренний сбой Gemini
не устранён, подтверждена именно обработка с ограниченными повторами.
Машиночитаемая сверка: `live/recovery-verification.json`.
