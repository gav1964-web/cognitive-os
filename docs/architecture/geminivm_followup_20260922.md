# GeminiVM: один вопросительный знак в том же диалоге

22 сентября 2026. Владелец показал, что после service_error отправка `?` в том
же чате дала JSON-кандидата примерно через30 секунд. Это наблюдение владельца,
не независимая приёмка ремонта humanize. По его поручению новая default-политика
GeminiVM: service_error_followup=true, service_error_probe=false.

После распознанного service_error провайдер один раз отправляет `?`, сохраняя
диалог, исходную задачу и выбранную модель. Полный prompt повторно не посылается.
Followup использует min(response_timeout, followup_timeout), по умолчанию300с.
При повторной ошибке или timeout цикл заканчивается, без нового чата, второго
вопросительного знака, арифметической диагностики или автоматического Answer now.
Обычный task timeout, UNKNOWN/login и refusal/stub не запускают этот механизм.

Обе отправки входят в общий max_attempts3. Предшествующий empty-page retry может
занять второй слот, тогда продолжение занимает третий. max_attempts1 или
service_error_retries0 отключает восстановление. Explicit probe=true выбирает
прежнюю арифметическую диагностику; оба флага false — прежние прямые повторы.
Таким образом старые режимы остаются явно выбираемыми, не вложенными fallback.

Перед отправкой native Firefox rich-text clipboard связывает последний ответ
с исходной ошибкой и фиксирует адрес существующего диалога. После `?` требуется
реально наблюдавшийся GENERATING, стабильный RESPONSE, тот же адрес и ровно один
добавленный model-response. Копируется нижний видимый toolbar, полученный текст
должен принадлежать последнему ответу из clipboard. Старый ответ, неверный адрес,
отсутствующая HTML-структура и comparison ambiguity завершают запрос ошибкой.
DOM, JavaScript и скрытые сетевые API не используются. Общая desktop lock
сохраняется на всю операцию; model selection в середине разговора не происходит.

Первоначальный отказ остаётся в attempt-1.json, новый результат имеет
kind=continuation. continuation.json хранит URL hash, число ответов и результат
проверок. HTTP/JSON добавляет continuation_count; он включён в retry_count,
а diagnostic_count остаётся0. Счётчики обозначают начатые попытки восстановления,
даже если последующая UI-проверка остановила ввод; реальные отправки — в events.
Качество кандидата проверяет потребитель, normal не является доказательством
корректности исправления. Usage неизвестен, прежние оценки ролей не повышаются.
