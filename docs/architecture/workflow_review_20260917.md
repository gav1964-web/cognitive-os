## Пять работ

1. **Контекст запрошенного workflow.** В прежнем лимите32000 символов сначала
   резервируются целые запрошенные выдержки до10000 символов каждая. Поддерживающий
   контекст получает остаток. Полнота относительно предоставленной выдержки
   записана отдельно от полноты исходника. Совпадающие полные секции двух чтений
   одного файла с одинаковым хешем используют одну гарантированно видимую копию
   через `covered_by`. Это не склейка разных версий или восстановление отсутствующего
   кода. Если лимита не хватает, сокращение остаётся явным.
2. **Итоговые утверждения.** `prepare_claim_review(..., claim_namespace='final')`
   и CLI `prepare --namespace final` выбирают текст после редактора. V4 поддерживает
   обе области, default остаётся draft; v1–v3 не меняют область. Exact claim и digest
   отчёта проверяются при привязке предложения. Final proposal не закрывает draft
   task с совпадающим ID. Читаемый отчёт различает соблюдение контракта и оценку модели.
3. **Документация и допуск фактов.** Плагин помечает основания каждого утверждения:
   ссылки на реализацию, документацию или другие источники. Текст без ссылки на
   реализацию получает предупреждение и не принимается в product_context как
   проверенный факт. Основания пересчитываются: подмена сохранённой пометки не
   обходит проверку. Это проверка типа свидетельства, а не понимание его смысла.
   Общая KB требует проверять конфликты README с выполняемым путём, предусловия
   и разницу между возвращённой проверкой и обеспеченным результатом. Имена и
   ожидаемые ответы конкретных проектов в политику не добавлены.
4. **Каталог чтений.** Review предлагает только поддерживаемые code/README paths,
   используя ту же функцию eligibility, что и reader. Собранные metadata/scripts
   могут остаться свидетельствами, но не рекламируются как доступный lookup.
5. **Измерение.** Новое полное описание Replay, контролируемый проект с ложным
   README и отдельный final-claim review старого ошибочного утверждения. Все
   исходники проверены по хешам, код описываемых проектов не выполнялся.

## Что происходит при неверном README

README сообщает замысел, но может отставать от проекта. Указание в KB — описывать
реализованный путь, а конфликт фиксировать в corrections/review; неизвестное не
подменять отсутствием возможности. Машинная граница дополнительно запрещает
принимать documentation-only claim как факт реализации для следующих ролей.
README автоматически не переписывается. Проверенный код тоже может быть неполным
или не соответствовать активной конфигурации: статическое чтение не является
наблюдением развёрнутого приложения. Наличие ссылки на код не доказывает тезис.

В `conflicting_readme/` README обещает CSV/XLSX, облако, принятие отрицательных
сумм и отсутствие пропусков некорректных строк. Код предоставляет локальную
функцию CSV, пропускает отрицательные/непреобразуемые значения, возвращает total
и skipped. COS описала этот путь и записала противоречия в corrections;
XLSX/облако не объявлены реализацией. Остались неточности: текст говорит
«положительные» вместо «неотрицательные» и повторяет разрешённые противоречия
в вопросах. Это один созданный ассистентом контроль, не независимый holdout.

## Replay и границы достигнутого

В новом полном описании сохранены ложная гарантия неизменности, опциональность
профиля и неверное число прогонов: два вместо двух baseline плюс fixed. Сняты
два поддержанных сценария работы с профилями. В живом review `_run_candidate`
с `baseline-2` и `collection_unchanged` уже был видим целиком. Ошибки нельзя
объяснить только отсутствием кода. Environment excerpt оставался сокращённым.

Отдельный final-claim review также подтвердил гарантию, процитировав сравнения
до/после. Ассистент отклонил предложение: функция возвращает flags, которые
могут быть false, и не обеспечивает заявленную универсальную гарантию. Ответ
модели не исправлялся задним числом. Решение — `final_claim_decision.json`,
читаемый разбор — `final_claim_adjudicated.md`. Product_context не создан.
