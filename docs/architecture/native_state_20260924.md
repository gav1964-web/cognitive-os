# Фактическое состояние при ремонте: 24 сентября 2026

Предыдущий ответ DeepSeek объяснял дефект одноэлементным кортежем, хотя вход
содержал два элемента. Добавлена проверяемая передача фактического состояния
в Analyzer, дизайн Architect и provenance спецификации. На живом повторе
**модель сохранила ошибочный диагноз; успешного ремонта и роста оценок нет**.

## Изменения

Расширен существующий `collect_native_repair_observations`, без второго
интерпретатора и без правил форматтера в общем runtime. Opt-in параметры
`source_files` и `preservation` включают `native_repair_observations.v2`:

1. Явно выбранные функции из нескольких файлов проверяются по исходникам и
   идентичности исполняемого кода. Список локальных переменных остаётся явным.
2. `native_observation_values.py` сохраняет ограниченную форму стандартных AST,
   позиции и размеры списков; также функцию и аргументы `functools.partial`.
   Пользовательские объекты/AST subclasses непрозрачны: без repr и свойств.
   Это структурное наблюдение Python, не доменное знание о форматтерах.
3. Приостановка generator фиксируется как `yield`; продолжение не создаёт
   ложного нового вызова. Выбранный callback и его выполнение — разные факты.
4. Исходный падающий тест и ранее проверенные preservation-тесты исполняются
   дважды в неизменных копиях. Сохраняются прежняя сигнатура сбоя, порядок и
   ожидаемые исходы каждого теста. Неисполненные выбранные функции показаны
   явно; в старом v1 условие полного покрытия не ослаблено.
5. Наблюдения проходят существующий diagnostic context в оба модельных запроса
   и provenance кандидата внутри TechnicalSpec. Полный receipt сохраняется;
   компактный контекст содержит изменения локальных значений без потери событий.

Владелец — Roles, механизм native diagnostics. Новых доменных KB, веток по имени
проекта и прав на изменение исходников нет. Старый API без новых параметров
сохраняет v1. Только для структурных наблюдений лимиты контекста составляют
64000 символов для гипотезы и96000 для кандидата; бюджет вызова отдельно
ограничивает размер сериализованных сообщений в байтах и выход модели.

## Наблюдаемые факты

`artifacts/role_state_20260924/observations.json`, `state-audit.json`:
один исходный сбой и шесть проходящих контрастов повторены дважды.
В падающем случае AST Tuple имеет два элемента, `is_one_el=False`, выбран и
исполнен `_fix_literal`. `_fix_tuple` не наблюдался ни в одном из семи случаев.
Работающие контрасты также используют `_fix_literal`: выбор другой функции
сам по себе не объясняет, как сохранить их поведение.

Первый сбор был отклонён: старое условие требовало исполнения каждой выбранной
функции, включая `_fix_tuple`. В v2 отсутствие исполнения стало явным
результатом наблюдения, а не выдуманным вызовом. Исходный заблокированный receipt
сохранён в `observations/`; успешные два повтора — в `observations-v2/`.

## Живой эксперимент

Сравнивается прежняя ответившая DeepSeek, основные профили ролей не менялись.
Перед запуском запросы проверены офлайн:57500 и69839 байт для короткого
технического примера ответа; второй реальный запрос формировался бы из модели.
Максимум два HTTP-запроса,96000 входных байт/32768 выходных токенов каждый,
без fallback, форматных и смысловых повторов. Резерв290304 токена.

Автоматический review первоначально отклонил внешний вызов. После проверки
публичного происхождения benchmark и постоянного разрешения пользователя
повторный review разрешил запуск. `outbound-scope-audit.json` фиксирует границу:
публичный `asottile/add-trailing-comma`, тестовые примеры и их receipts;
исходники COS, машинная конфигурация, переменные окружения и ключи не передавались.

**Результат:1 запрос,24,953с,18170 сообщённых токенов** (17925 вход/245 выход),
`scope_review_required`. DeepSeek вновь утверждает «single element» и просит
трассу одноэлементного кортежа. Это противоречит переданным наблюдениям.
Модельного дизайна/патча нет, второй слот не использован, исходный проект
не изменён. Gateway сообщил cache miss; usage — telemetry, не счёт провайдера.
Вход относительно прошлого ответа DeepSeek вырос8492→17925 токенов, при этом
фактическое противоречие сохранилось. Это не свидетельство пользы большего контекста.
Evidence: `protocol.json`, `prompt-audit.json`, `calls.json`, `role-run.json`,
`live-summary.json` в каталоге этапа. Негативный ответ не исправлялся ассистентом.

## Проверка и дальнейшее решение

Тесты покрывают фактическую форму AST, callback binding/исполнение, generator
resume, сравнение с сохранённым случаем, неподдерживаемые объекты, изменение
receipts/исходников/области наблюдения и полную передачу через ролевую цепочку.
Итоговый receipt и counts: `artifacts/role_state_20260924/verification.json`.
Все проверки остаются trusted-code replay, не защитой от враждебного кода.
Не поддержаны произвольные объекты, async, произвольные class-based тесты или
полная трасса всех функций проекта. Отсутствие вызова ограничено выбранными
тестами и фазой call, оно не доказывает глобальную недостижимость функции.

Добавление фактического контекста не помогло в этом повторе. Нельзя дальше
объяснять ту же ошибку исключительно отсутствием AST/trace и расширять prompt
без измерения. Следующий отдельный эксперимент: короткий запрос Analyzer на
интерпретацию нескольких наблюдаемых фактов до запроса ремонта, с измерением
противоречий; затем сравнение отвечающих моделей на одном фиксированном входе.
Не добавлять проверку фразы «single element» в общий runtime. Перейти к дизайну
и патчу только после корректной интерпретации фактов. Это гипотеза следующего
этапа, не уже проверенный способ улучшения качества.
