# Пакет: границы частей, связи реализации и реальный проект

Дата: 17 сентября 2026. Продолжение [v3](claim_review_v3_20260917.md).
Рабочие артефакты: `artifacts/claim_transfer_20260917/`.

## Пять работ

1. **Выравнивание границ частей.** Новый v4 сохраняет raw response и сопоставляет
   части с исходным утверждением. Можно восстановить только ASCII-пробелы,
   табуляцию и переводы строк на границах частей. Слова, отрицания, порядок,
   пунктуация и внутренние пробелы остаются строгими. Нельзя склеить `1 00` в100
   или `can not` в cannot. Результат содержит позиции частей и все изменения;
   повторная проверка proposal проверяет и этот журнал. Старые v1/v2/v3 сохраняют
   правила. Отдельная offline-проекция прежнего отказа не является живым ответом.
2. **Связи реализации в локальной KB.** Инструкция v4 различает сам вызов и
   поведение реализации за вызовом. Для утверждения о реализации нужны её код
   и привязка; утверждение только о прямом вызове не требует скрытого кода.
   Это модельная оценка, не автоматическое доказательство Python dispatch.
3. **Пять замороженных контрастов.** Неизвестный backend, явные Memory/Writer,
   только прямой вызов и условный выбор Memory/Disk. По одному DeepSeek-запросу,
   timeout240, без retry/fallback. Контракт5/5, вердикты4/5. В case04 обе части
   supported, но bindings ошибочно missing, поэтому общий uncertain вместо
   supported. Усиленная инструкция не устранила проблему применимости coverage.
4. **Общий бюджет для адаптивного описания.** BudgetedChat резервирует слоты
   будущих запросов с пределом UTF-8 байтов и выходных токенов. Точные сообщения
   сохраняются перед вызовом, usage попадает одновременно в receipt и общий
   ledger. Нет скрытых fallback; лишние/большие запросы и неизвестный расход
   останавливают цепочку. Обычный describe_project не меняется без адаптера.
5. **Проверка полного описания реального компонента.** Cognitive Inspect —
   существующий отдельный многомодульный пакет с CLI и четырьмя Python API.
   Это знакомый внутренний проект, не независимый holdout. Исходники сохранены
   по хешам; критерии полноты заморожены отдельно и не передаются модели.

## Результат на реальном проекте

Обычный describe_project завершился успешно за три запроса (черновик, запрос
источников, финальный review),51157 reported tokens. COS описала назначение,
четыре API, отдельный tree-only CLI, входы и выходы. Все пять заранее записанных
основных фактов покрыты по сверке ассистента. Исходники Cognitive Inspect не
изменились. [Сохранённое описание](../../artifacts/claim_transfer_20260917/description.md)
не исправлялось вручную.

Есть два конкретных пропуска полноты: review убрала примеры Flask/FastAPI и
установки зависимостей. В исходном контексте были тела `_frameworks` и `_purpose`,
но в обоих запросах review их уже нет. Дополнительное чтение только функций
`run` возвращает вызовы helpers, а не их определения. Это подтверждённая потеря
контекста; не доказательство, что модель отвергла находившийся перед ней код.
Матрица видимости и смысловые замечания сохранены в `real_review.json`.
Также стоит яснее маркировать AST-эвристики и убрать лишний вопрос о выборе
между уже существующими API и CLI.

Пять проверенных утверждений полного описания и заметки о пропусках прошли через
реальные детерминированные Analyzer → Architect → SpecWriter. Источники, digest
контекста и execution_authorized=false проверены; дополнительных LLM-вызовов нет.
Это проверка передачи понимания продукта, не измерение качества дизайна ролей.

Итого пакет:8 запросов,58972 reported tokens (53516 входных,5456 выходных),
суммарная задержка172,868с. Весь расход известен, ниже резерва632483 и порога
миллион. Все пять работ выполнены; обе живые серии закрыты. Итог контрастов4/5
не является улучшением относительно другой выборки v3. Полный description route
не использует v4 автоматически, поэтому его результат не приписывается новому
контракту отдельных утверждений. Независимой сертификации9.7+ нет.

## Следующий приоритет

Сохранить нужные тела вызываемых helpers в ограниченном контексте review и
не тратить дополнительное чтение на уже известную оболочку `run`. Вначале
воспроизвести обе потери offline на сохранённых сообщениях, затем проверить общий
механизм на другом небольшом многомодульном проекте. Не добавлять в KB названия
конкретных функций или ответы для Cognitive Inspect. Для claim review отдельно
проверить применимость bindings к утверждению только о прямом вызове; ошибка
case04 остаётся открытой. Очередная настройка схемы без проверки полезности полного
описания не является приоритетом.
