## Механизмы

`development_quality 0.1.8` владеет правилом `repair_metadata`. Оно выводит только
отсутствующее `regression_policy: new_preservation_only`, когда runtime передал
полный inventory без существующего тестового набора, модель выбрала пустой список
регрессии и объявила preservation case. Явное значение, даже ошибочное, не
заменяется. Отсутствующий inventory не является доказательством отсутствия тестов.
Исходное и нормализованное значения сохраняются с хешами. Аудит и native
qualification обязательны; содержание тестов правило не меняет.

Повторённые полные тела тестов в запросе заменяются точными ссылками с хешами;
обратное развёртывание проверяется на равенство исходному payload. Семантическое
сокращение исходников или удаление контрпримеров этим механизмом не выполняется.
SpecWriter также может вернуть hash-bound ссылку на неизменный ранее принятый
тест. Новый тест всегда требует полного модельного содержимого. Runtime разворачивает
ссылки до аудита, проверки неизменности и native execution; исходный ответ сохраняется.

На исторических запросах новая входная сериализация оказалась на2352 байта больше
прежней из-за хешей: самостоятельного выигрыша input-cost здесь нет. Отдельный
контрфактический опыт на13 сохранённых ответах показывает уменьшение JSON с233859
до116556 байт при ссылках на замороженные тесты. Это измерение сериализации,
не фактическая экономия inference. Живое использование учитывается отдельно.

Профильная проверка перед заморозкой:74/74 в отдельном снимке;
квитанция пакета — `stage-pre-cohort.json` и её source inventory.

После зачётного прогона добавлены общие механизмы восстановления:

- Однозначное исправление номера строки дословной цитаты в уже переданных
  исходниках. При неоднозначности или изменении текста модель исправляет ответ сама.
- Ошибочное изменение замороженного теста Programmer возвращается этой роли;
  изменение не принимается и защита неизменности не ослабляется.
- Возобновление native-проверенного кандидата с новым Reviewer после остановки
  на лимите или после одобрения, включая частично достигнутую цель. Исходники,
  frozen tests и кандидат перепроверяются. Прежнее одобрение не переносится.
- Reviewer получает контракт поставки: production diff и отдельный список хешей
  замороженных тестов. Runtime включает обе части в поставку. Само сообщение
  не утверждает, что установка уже выполнена.

### Остаточные ограничения и следующая задача

В callable_dump найден пробел координации Challenger: первый пакет содержал
корректный выживший контрпример `dict-subclass-identity` и другой некорректный
мутант. Повтор заменил пакет; обязательным остался только новый контрпример
falsey callable. История первого сохранена, но не стала обязательной для
SpecWriter. Текущая реализация сохраняет dict subclasses; установлен пробел
покрытия, а не дефект конечного production-кода. Задача зарегистрирована в
`DEVELOPMENT_TASKS.json`: `challenger-preserve-valid-survivors-across-invalid-retry`.
Следующий шаг — накопительный набор проверенных обязательств с привязкой к
кандидату и offline-регрессия смешанного valid/invalid пакета.

Не следует повторять эти шесть закрытых задач ради повышения баллов. Следующая
проверка автономности должна использовать новые заранее зафиксированные задачи,
после устранения указанного пробела и пакетирования замечаний аудита.
