### Почему изменилось решение Reviewer

Первый review после повышения лимита отверг содержимое вне `<model-response>`:
оно якобы могло быть потерянной частью ответа. Ассистент преждевременно направил
это замечание SpecWriter. Четыре вызова израсходовали171405 токенов; новый набор
не был принят из-за ошибок ссылок на регрессии и изменения неизменяемых тестов.
Эта ветка сохранена, ни один её тест/патч не установлен и не объявлен успешным.

После проверки `cleanup_native.SCRIPT page()` и полного сохранённого `page.html`
оказалось, что вход — HTML всей страницы, а не только ответа. В нём6 корневых
элементов и3 ответа глубоко внутри оболочки приложения. Неизменённый кандидат
через production `snapshot()` разобрал все3; последний точно совпал с toolbar copy.
Вырезанная fixture сама по себе не показывала это окружение. Простой запрет
внешних узлов мог бы сломать настоящую страницу; сама их отбраковка не следует
из требования полноты ответа, явно ограниченного `<model-response>`.

Эта новая проверка передана Reviewer с привязкой к исходникам, кандидату и файлам
записи. Reviewer **сам пересмотрел отрицательное решение**, указав причину.
Ручного обхода review, изменения критерия результата или редактирования целевого
патча нет. Внутри ответов продолжают действовать строгие проверки принадлежности,
неизвестных структур и полноты текста. Вывод процесса: прежде чем запускать ремонт
по замечанию модели, сверять его с реальным входным контрактом; review тоже ошибается.

## Почему кандидат не принят

clipboard, а частичная копия всё равно принимается. Тесты покрывали неизвестное
содержимое внутри panel, но не соседние элементы вне него.

Ассистент отдельно воспроизвёл замечание через публичный API и скриптовый
транспорт: неизвестный текст перед `</message-content>` и перед
