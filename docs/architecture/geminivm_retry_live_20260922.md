# Живая проверка GeminiVM после добавления повторов

22 сентября2026. По «дальше» владельца выполнен новый ограниченный этап:
1 HTTP-запрос через шлюз5, до3 отправок только внутри GeminiVM. Предыдущий
пакет из8 вызовов остаётся закрытым, его бюджет и результаты не переписаны.

Задача — публичный python-humanize/humanize, исправление metric. Сохранённый
диагноз переиспользован как consumed evidence. Перед живым вызовом весь список
messages сравнивается с ранее отправленным `fresh-recovered` payload. Исходный
корпус, baseline, требования и тесты неизменны; ассистент не пишет патч за модель.

Перед отправкой проверен штатный Network Monitor: экспорт10 реальных HTTP-записей
и включённый Persist Logs. Отдельное окно свёрнуто; размеры основного окна
Gemini не менялись. После запроса сохранены197 записей — только метод, host/path
без query, статус, длительность и timings, без HAR-тел/headers/cookies.
Консоль закрыта, Persist Logs выключен. Новых браузерных скриптов или прямых
обращений к внутреннему API Gemini не выполнялось.

Результат: **controlled_stop / provider_unavailable**, всего123.453с.
HTTP-вызов занял118.316с, GeminiVM run `20260922T111119-ac33975ec32b`.
Модель Pro ответила: «I encountered an error doing what you asked. Could you
try again?» Ответ корректно скопирован: transport_status=ok,
response_status=service_error, retry_count=0. GeminiVM/шлюз вернули HTTP502,
COS сохранила диагноз отказа и quality_evaluation=not_evaluated.

Пустой страницы в этой попытке не было, поэтому новый empty-page retry не
проверен живым воспроизведением. Существующий service_error_retries=0 сохранён;
явная ошибка сервиса не превращена в потерю страницы и не запустила повтор.
Автономные338 тестов предыдущего этапа остаются проверкой механизма3 попыток.

Наблюдение Network Monitor: запрос `geminiweb-pa.clients6.google.com/v1/processSession`
начался11:12:20.977 UTC, завершился с HTTP200 за43.553с. Это транспортное
завершение запроса, не успешный ответ модели. В197 записях нет HTTP4xx/5xx;
шесть записей со статусом0 не доказывают конкретную причину отказа. Эти данные
не устанавливают источник прежнего возврата на главную или внутреннюю причину
сообщения Gemini. Диагностика чтения/отправки сработала в текущем прогоне.

Итог для COS: кандидат не получен, humanize не исправлен, общие оценки первых
трёх ролей не изменяются. Новых генераций после этого отказа нет; usage остаётся
неизвестным. source_unchanged=true. Развитие ролей сейчас ограничено отказом
используемой модели в этом конкретном запросе, а не результатом native-тестов.

Evidence: `artifacts/geminivm_retry_live_20260922/`: `protocol.json`, `budget.json`,
`calls.json`, `reuse.json`, `summary.json`, `preflight-network.json`,
`request-network.json`, `restored-content.png`. Runner `run.py` запрещает второй
HTTP-вызов и изменение текста публичного запроса.

Следующее решение по устойчивости следует принимать явно: повтор service_error
уже поддержан GeminiVM и ограничен тем же max_attempts, но сейчас выключен.
Не добавлять для обхода отказа дополнительный цикл в COS/шлюз и не повышать
оценки ролей за корректную доставку сообщения об ошибке.
