## Контрпримеры

`runtime/feature_quality_challenge.py` сохраняет все native-валидированные
варианты, как выявленные текущими тестами (`killed`), так и выявляющие недостаток
покрытия (`survived`). Исправленный ответ Challenger объединяется с ними;
совпадающие объекты устраняются только по точному digest. Имена вариантов сами
по себе не являются идентичностью. Содержание модели не исправляется вручную.

Один модельный ответ по-прежнему содержит1..3 варианта, число попыток2.
Объединённая кампания ограничена6 вариантами, проверяется группами до3 без
усечения. Порядок предложений и результатов совпадает, поэтому SpecWriter
получает свидетельство именно соответствующего контрпримера. При расширении
тестов повторно выполняется вся кампания, пока production-хеши неизменны.

Пустой ответ, ошибка исполнения свидетельства или изменение кандидата не дают
одобрения. Даже если повторная проверка стала неопределённой, прежнее обязательство
остаётся в журнале. `*-retained.json` связывает определения с inventory кандидата
и квитанцией проверки; `grants_approval=false`. Это журнал текущего ограниченного
цикла, не механизм автоматического доверенного возобновления произвольного
удалённого процесса по одному этому файлу.

## Замечания к SpecWriter

Прежде исчезновение случая из неутверждённого черновика останавливало проход до
содержательного аудита. Даже синтаксически правильный ответ мог потребовать
отдельного следующего круга для обнаружения другой проблемы покрытия.

Теперь структурно допустимый черновик передаётся аудитору вместе с обнаруженными
нарушениями преемственности (`known_admission_issues`). Аудитор проверяет остальные
содержательные требования в том же проходе. SpecWriter получает объединённую
обратную связь. Одобрение аудитора не снимает детерминированного замечания.

Краткий список прежних замечаний (`prior_audit_issues`) сохраняется при очередной
ошибке формата и чтении исходников, пока goal/design/source binding тот же.
Это история для переоценки, не вечный список обязательных требований: аудитор
должен отличать исправленные и неподтверждённые замечания от оставшихся дефектов.
При смене привязки или успешном допуске контекст сбрасывается прежним механизмом.

Ошибки синтаксиса, изменение принятых frozen tests и отсутствие обязательного
native-свидетельства отклонённого кандидата по-прежнему останавливают работу
**до платного аудита**. После допуска неизменными остаются native qualification,
проверка baseline, Programmer, Reviewer и внешние проверки.

Знание аудитора принадлежит `development_quality0.1.9`; runtime только передаёт
контекст и объединяет результаты. Публичные API целевых проектов не менялись.

### Что измерено, а что ещё нет

Детерминированный сценарий показывает два независимых замечания в одной обратной
связи вместо отложенного второго аудита. Проверены сохранение полного черновика,
работа через запрос чтения и невозможность снять запрет одним `approve`.
Однако реальная экономия токенов пока не измерена. Если кроме исчезнувшего случая
других проблем нет, объединённый аудит может оказаться дополнительным вызовом.
Поэтому стоимость и число обращений надо сравнить на новой фиксированной выборке,
а не объявлять экономию из одного теста маршрутизации.
