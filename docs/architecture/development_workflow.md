# Продолжение разработки и устойчивость LLM

Вход в рабочий этап: `python tools/development_stage.py begin`.
Команда собирает незакоммиченные пути, задачи, подходящие подсистемы, тесты из
карты и предыдущий результат. Неизвестные карте файлы перечисляются отдельно.
Рекомендация тестов основана на карте; она не доказывает полноту динамических
зависимостей. Машинный config.json, .env и артефакты не входят в список исходников.

Завершение: `python tools/development_stage.py finish --test-target tests/runtime/test_llm_failover.py
--summary "Проверено переключение моделей"`. Команду вводить одной строкой.
Проверяются finalization и регрессии в копии. Падение тестов создаёт обязательную
задачу с ссылкой на результат. `artifacts/development/stage-latest.json` указывает
последний этап. Прямой finalizer остаётся проверкой размера/очереди и не заменяет
регрессионные тесты при отсутствии превышений.

С 12 сентября receipt этапа содержит `source_provenance`: путь и SHA-256 полного
`source-inventory.json`, хеши всех включённых файлов, HEAD, версию и путь Python,
платформу и явно подключённые pytest-плагины. Тесты проверяют именно эту копию;
изменение исходников во время проверки делает этап неуспешным. HEAD без inventory
не описывает незакоммиченную версию. Последующее изменение файлов создаёт новую
версию и не расширяет область уже полученного результата.

Копия предназначена для воспроизводимости доверенных тестов. Процесс сохраняет
права текущего пользователя, может обращаться к сети и писать за пределами копии;
наследуемое окружение не считается очищенным от всех секретов. Для недоверенного
кода нужен отдельно настроенный OS/container runner. Этот этап его не реализует.

Очередь DEVELOPMENT_TASKS.json поддерживает структурные задачи, ошибки тестов,
архитектуру, документацию, провайдеров, оценку и функциональные доработки.
`task` создаёт или обновляет запись по устойчивому ключу; `--depends-on` принимает
ID предшествующей задачи. Циклы отклоняются. `close --id ID --evidence receipt
--summary result` проверяет наличие доказательств и закрытие зависимостей,
сохраняет хеши. Качество выбранных доказательств подтверждает ответственный
ассистент; наличие файла отчёта само по себе не является сертификацией.

Решения сохраняются командой `remember --key NAME --decision TEXT --rationale TEXT
--path FILE --reconsider-when CONDITION`. Хеши привязанных файлов определяют
актуальность; `needs_review` выводится в контексте после их изменения. Этот слой
памяти описывает инженерные решения, а существующая project_development_memory
продолжает хранить результаты ролевых запусков с прежними условиями допуска.

## Согласованные принципы дальнейшей работы — 15 сентября 2026

Главный критерий — проверенный результат для пользователя. Общий размер системы
и число компонентов вторичны: дополнительная сложность допустима, если помогает
получать результат и её последствия можно проверить. Разработка с помощью LLM
не устраняет скрытые зависимости, противоречия контрактов и устаревшие предположения.

Для каждой задачи нужен ограниченный, но достаточный локальный контекст:
ответственность компонента, входы и выходы, инварианты, разрешённые зависимости,
потребители и проверки последствий изменения. Поддерживаем его через карту,
краткие описания подсистем, очередь и привязанные к исходникам решения. Наличие
доступа ко всему репозиторию само по себе не доказывает понимания поведения.

Разбиение на модули, плагины или подпроекты должно выделять такие границы и помогать
локальному изменению и проверке. Не вводим новые слои ради количества компонентов
или красивой схемы. Финальный предел 400 строк в Python-файле сохраняется;
механическое дробление с запутанными связями не считается улучшением понимания.
При необходимости выбираем осмысленное разбиение и проверяем затронутые контракты.

«Компрессированная компетентность» остаётся проверяемой гипотезой. Повторяемость
решения ещё не доказывает надёжность. Перенос в детерминированный механизм требует
явной области применимости, проверки результата и условий отказа или возврата
к LLM. Обобщение кейсов проверяем на новых случаях и на сохранении прежнего
поведения; единая оболочка над растущим деревом исключений не доказывает обобщения.
Не предполагаем, что область неизвестного всегда сокращается: оцениваем снижение
потребности в LLM при сохранении качества на сопоставимых задачах.

Измеряем успешность полного цикла, регрессии, стоимость и задержку, включая
диагностику, проверки, повторные попытки и сопровождение. Уменьшение числа вызовов
LLM не заменяет этих результатов. Новые архитектурные слои обосновываем конкретной
задачей и проверкой пользы. Успешное отклонение плохого патча учитываем отдельно
от успешного автономного исправления; документация и harness-тесты не повышают
сами по себе продуктовые оценки ролей.

## Владение знаниями

Принят [подход с локальными KB плагинов компетенций](plugin_owned_knowledge.md).
Для нового предметного знания определяем владельца, алгоритм применения,
контракт и проверки. Общий интерпретатор остаётся предметно нейтральным;
общая инфраструктура хранит каталог, контекст задачи и журнал доказательств.
[Первый pickle-пилот](pickle_competency_20260915.md) выделяет рабочий механизм
вместе с KB; исследовательские инструменты пока используют typed API владельца.
Оставшаяся миграция отслеживается в DEVELOPMENT_TASKS.json; оценки ролей
изменяются только по результатам поведенческих измерений.

Уточнение пользователя: этап разделения принимается по границам ответственности,
контрактам и сохранению поведения. Прирост качества, экономия inference и внешний
benchmark не являются условиями продолжения структурной миграции. Исправление
выявленного дефекта планируется отдельно от переноса функционала.

## Основная и резервная модели

Перед живыми модельными запросами ассистент обязан проверить и при необходимости
запустить локальный шлюз штатной функцией `ensure_llm_gateway_for_url`. Запуск
ранее разрешён пользователем; отсутствие процесса само по себе не требует его
вмешательства. Параметры находятся в `config/llm_gateway_bootstrap.json`.
Готовность проверяется через health endpoint, процесс запускается без окна.
`BudgetedChat` выполняет эту проверку до `start_call` для штатного транспорта:
ошибка запуска не превращается в неизвестный расход inference. Внедрённый
транспорт (например, тестовый) отвечает за собственную готовность.
Необходимо сохранять старые ошибки и учитывать неопределённый расход отдельно;
успешный перезапуск не является основанием переписывать прежний usage как ноль.

Профиль L4.5 использует DeepSeek, затем `gigachat_pro_backup` с моделью
`GigaChat-Pro` через тот же локальный шлюз. ID резервной модели подтверждён
списком `/models`; запрос к ней прошёл через `/chat/completions`.
Профили имеют отдельные параметры формата ответа и имена переменных ключа.
Резерв не получает ключ основного профиля через неявное копирование.

Переключение допускается при 402, 408, 429, 500, 502, 503, 504 и транспортных
сбоях; 400/401/403/404/422, неверный JSON, усечение и ошибки TLS-сертификата
остаются ошибками. Ошибка запроса не маскируется другим ответом модели.
В одном вызове каждый маршрут пробуется не более одного раза, всего до трёх
маршрутов. Пауза проблемного маршрута — 60 секунд, для 402 — час; Retry-After
может её увеличить до суток. Пауза хранится в процессе, не переживает его
перезапуск. После истечения основная модель снова получает первый запрос.
Переключение не возобновляет оборванную генерацию: резерв получает исходный запрос.

Записываются ошибки попыток и фактический model/provider успешного ответа,
признак fallback, время и сообщённые провайдером токены. Тексты запросов, ключи
и тела HTTP-ошибок в этих событиях отсутствуют. Нулевой расход токенов, сообщённый
шлюзом, не доказывает отсутствие стоимости. Новая модель проходит те же проверки
JSON/плана и sandbox; её ответ не получает дополнительных полномочий.

Внешние контракты сверены 10 сентября 2026:
[DeepSeek errors](https://api-docs.deepseek.com/quick_start/error_codes/),
[GigaChat errors](https://developers.sber.ru/docs/ru/gigachat/api/errors-description).
При другом шлюзе нужно проверить его отображение ошибок и имена моделей.

## Диагностика и проверка исправления

`tools/reduce_failure_fixture.py --project PATH --fixture input.bin --test-target
tests/test_reader.py` уменьшает только явно выбранные входные данные в копии.
Два исходных повтора, прежняя коллекция, тип/сообщение падения и финальный повтор
должны совпасть. По умолчанию максимум 24 кандидата; исходный проект не изменяется.
Это локализация входа, а не доказательство причины и не готовое исправление.

`tools/review_project_fix.py` связывает Inspect и Replay: требуются явные hashes
baseline/fix, тестовые и production-файлы, полный набор совместимых wheels и
путь отчёта. Например, одной строкой:

```bash
python tools/review_project_fix.py --root . --project projects/example --baseline BASE_HASH --fix FIX_HASH --test tests/test_example.py --production src/example.py --wheel-directory wheels --output artifacts/fix-review.json
```

Вместо каталога `--wheel` повторяется для полного замыкания зависимостей; имена файлов wheels
должны соответствовать настоящим дистрибутивам. Репозиторий должен быть чистым
и находиться внутри root и разрешённой Inspect области текущего каталога.
Результат `verified` означает повторение дефекта, успешные выбранные тесты с
заданным исправлением и сохранность исходников. Самостоятельное нахождение
исправления системой этим сценарием не измеряется.

## Linux CI

Обычные unit/contract tests должны работать на чистом checkout с requirements-dev.
Временные проекты pytest создаются внутри `.pytest-tmp`, сохраняя реальные
ограничения области Inspect. Исторические измерения, которым нужны неотслеживаемые
локальные данные, помечены `local_corpus` и пропускаются с явной причиной при их
отсутствии. Такой skip не является успешной независимой оценкой. Unit-проверки
правил допуска используют синтетические входы и продолжают работать в CI.

Путь исполняемого Python сохраняет идентичность virtualenv: разрешение его symlink
до системного бинарника теряет окружение. Родитель basetemp создаётся корневым
pytest hook; каталог процесса plugin check отделён от очищаемого pytest каталога.
Plugin check ограничивает загрузку conftest своим workspace, чтобы родительский
checkout не подменял импорты при проверке вложенной копии.
Тесты шаблонов используют fixtures вместо случайных обращений к живой LLM.
Проверка собственного loopback HTTP-сервера обходит proxy. Если сама среда не
поддерживает TCP loopback, её результат сохраняется отдельно и не объявляется
зелёным Linux CI.
