# Форма описания и проверка Replay: 17 сентября 2026

Пакет из пяти работ завершён. Контур описания проходит прежний отказ формы,
но новый результат Replay не принят ассистентом после чтения исходников.
Рост качества и баллов ролей не установлен. Основной receipt:
`artifacts/description_shape_20260917/summary.json`; проверки: `verification.json`.

## Выполненные работы

1. **Контракт плагина.** `project_description`0.9.0 владеет правилом в своей KB:
   одиночный объект утверждения в `scenarios`/`data_flow` разрешено завернуть
   в список. Текст, ссылки, порядок и остальные поля не меняются. После этого
   действует прежняя строгая проверка количества, типов, длины и известных ссылок.
   Не поддерживаются извлечение JSON из прозы, удаление полей и догадки о ссылках.
2. **Полный маршрут.** Правило применяется к черновику и `description` итогового
   review. Исходные ответы и review rounds сохраняются; отдельный receipt содержит
   операции, digest исходного/приведённого JSON и `semantic_verified=false`.
   Нормализация не заменяет review и не предоставляет полномочия исполнения.
3. **Последующие потребители.** Offline audit, review отдельного утверждения,
   отображение снятых утверждений и product_context используют одну проверку
   происхождения. Приведённый draft повторно выводится из raw; при изменении
   receipt или итогового текста относительно raw review происходит отказ.
   Старые отчёты без receipt читаются строго: исторический failed не превращается
   задним числом в успешное описание. Digests проверяют согласованность, не авторство.
4. **Сохранённый отказ и контрпримеры.** Добавлен переносимый raw fixture Replay
   и тесты на неизвестные ссылки, дополнительные поля, пустые/длинные утверждения,
   неполный review, подмену результата и сохранение снятого claim. Отдельный
   синтетический review исправляет ложное утверждение: форма не утверждает смысл.
5. **Измерение и разбор источников.** Выполнена новая ограниченная серия Replay,
   исправлено обнаруженное рассогласование README lookup, итог сверён с исходниками.
   Подготовлены три source-bound задания следующего review без model calls.

## Измерение

Первый новый прогон: черновик взят шлюзом из кеша, совпадает с прежним запросом
и raw. `data_flow` приведён без изменения содержания. Следующий запрос модели
попросил два чтения кода и README из предложенного каталога. Чтение README
было запрещено обработчиком: `description_lookup_path`. Этот failed receipt
сохранён отдельно и не переписан.

README теперь можно читать диапазоном, с прежними ограничениями пути, хеша,
размера и редактированием credential-литералов. Разрешены README без расширения,
`.md`, `.rst`, `.txt`; произвольные документы не добавлены. Такие выдержки имеют
`documentation_claims`, а не доказательную роль исходного кода. Поиск литералов
для опровержения review не использует их как код. Существующий каталог также
содержит metadata/scripts, не все из которых разрешены lookup: это отдельное
оставшееся рассогласование, не заявляется полностью решённым.

В отдельном эксперименте повторно использованы два сохранённых ответа локально,
только при точном совпадении запросов. Один оставшийся запрос получил финальный
review. Это не новый независимый полный прогон. Файлы: `replay_description.json`
(отказ), `continuation_description.json`/`.md` (полученный текст),
`continuation_execution.json` (условия повторного использования).

1769 выходных. Суммарная задержка61,643с. Резерв449652, не гарантия биллинга;

## Что осталось неверным

`semantic_review.json` содержит выводы ассистента по полным исходникам:

- Неизменность репозитория названа гарантией. API возвращает сравнения состояния
  и признак cleanup, которые могут быть false; потребитель должен проверить их.
- Прохождение тестов объявлено достаточным для квалификации. Нужны также повтор
  baseline и сохранение набора тестов; два baseline-прогона явно не описаны.
- Опциональный Python-аргумент профиля принят за возможность успешного запуска
  без профиля. `prepare_environment` обязательно валидирует профиль; пустой
  профиль приводит к отказу подготовки.
- Oracle описан как содержащий патчи. Он передаёт revision, пути и хеши;
  патчи вычисляются из Git. Различие worktree/venv и OS security sandbox не названо.

Причина не сводится к «модель плохо прочитала весь код». `source_visibility.json`
показывает: lookup получил полное `_run_candidate`, но следующий отбор в32000
символов снова убрал длинную функцию из видимого review. README сократился до255
символов. Сравнения source-invariant flags остались в x2, однако гарантия всё
равно не исправлена. Видимость контекста и качество смыслового review — две
разные оставшиеся проблемы. Снижение расхода не измерялось как эффект изменения.

## Следующий пакет

Сначала сохранить в review условия именно запрошенного workflow, включая длинные
функции, не заполняя бюджет только короткими helpers. Затем проверять итоговые
утверждения и их предусловия: сейчас отдельные review jobs относятся к draft,
поэтому не покрывают новую ошибку, внесённую финальным редактором. Подготовленные
`next_*_job.json` помечены этим ограничением и не исполнялись.

Отдельно согласовать advertised lookup catalog с реально поддержанными чтениями.
Не добавлять правила с именами Replay или ожидаемыми ответами в production KB.
До принятия purpose не передавать этот результат как проверенный product_context
Analyzer → Architect → SpecWriter. Старые положительные измерения Inspect и
исторические оценки ролей не заменяют эту проверку.
