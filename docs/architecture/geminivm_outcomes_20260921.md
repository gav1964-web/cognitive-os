# Обработка неполезных исходов GeminiVM в 5 и COS — 21 сентября 2026

Проблема: GeminiVM уже различает `normal`, `service_error`, `refusal` и
`suspected_stub`. Его HTTP API намеренно доставляет refusal/stub с HTTP200,
текстом и `success=false`. Шлюз раньше принимал эти ответы как успешный результат,
а COS пыталась извлечь JSON. Даже объект внутри отказа мог стать результатом задачи.

Исправлена обработка в потребителях; классификатор и браузер GeminiVM не менялись.

| Исход GeminiVM | Прямой запрос через5 | geminivm_resilient |
|---|---|---|
| normal | Обычный ответ | Обычный ответ |
| refusal | HTTP422, code=refusal | Остановка, без подмены модели |
| suspected_stub | HTTP422, code=suspected_stub | Следующий кандидат, cooldown текущей модели |
| service_error | HTTP502 с исходным code | Прежний ограниченный fallback |
| success=false с противоречивым/неполным статусом | HTTP502, provider_response_unusable | Ошибка протокола, не успешный результат |

Преобразование выполняется в GeminiVMAdapter до возврата ProviderResult, поэтому
отказ не попадает в успешный результат, кеш или успешный ответ `/chat`.
Прямой маршрут не запускает резерв. Resilient-профиль остаётся явным выбором,
с максимум тремя кандидатами. В его failover_on добавлен только suspected_stub;
refusal сам по себе не вызывает повтор или переход к другой модели.
Исходный текст остаётся в журнале GeminiVM; run_id и ограниченные diagnostics
передаются в ошибке шлюза. Текст не теряется из первичного свидетельства и
не копируется в служебную телеметрию COS.

COS дополнительно проверяет объявленный response_status в provider_diagnostics
даже при HTTP200, до разбора content. В shared runtime нет текстовых шаблонов
GeminiVM или специальных веток по имени провайдера. Проверяются явные статусы;
полезный normal-ответ с обсуждением отказов не отклоняется по ключевым словам.
HTTP200/422 с известным неполезным исходом сохраняет структурированную причину,
останавливает цикл разработки и сохраняет задачу для продолжения. Качество решения
не оценивается. Автоматический COS failover на эти200/422 не добавлен: резервная
политика для suspected_stub принадлежит явно выбранному профилю шлюза.
Сообщённый usage при HTTP200 сохраняется даже при отклонении результата.
