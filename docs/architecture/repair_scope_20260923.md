# Проверка причинного диагноза и области ремонта, 23 сентября 2026

В известной задаче add-trailing-comma точка наблюдения `_main.py:_fix_src`
оказалась чрезмерно узкой обязательной областью правки. Два сохранённых intake
повтора связывают её с тестом через `unique_assertion_causal_call`. Это корректная
привязка наблюдаемого API, но не доказательство внутреннего места дефекта.
В последних ручных экспериментах ассистент потребовал менять только эту функцию.
Такое ограничение было нашей ошибкой постановки задачи; оно не доказывает,
что исправление в этой функции вообще невозможно, и не объясняет все ошибки модели.

## Причина, подтверждённая локальным экспериментом

Зафиксированная baseline из `artifacts/role_quality_20260922/comma-composition-v2`
проверена по сохранённому inventory. Версия Python — 3.10.11; upstream-решение
не читалось. Для `x = (\n    object\n), object\n`:

1. AST внешнего Tuple начинается в `(1, 4)`, первый элемент Name — в `(2, 4)`.
2. `visit_Tuple` выбирает `_fix_literal` на открывающей скобке первого элемента.
3. Этот callback добавляет запятую внутри скобок и превращает Name в Tuple.
4. Общий проход `_fix_src` получает уже изменённый AST; он не является источником
   добавленной запятой в этом примере.

Трасса захватывает текст до и после каждого callback. Результат обёрток сверен
с обычным вызовом исходной функции. Проверены дефектный пример, обычный список,
настоящий tuple и обе последовательности tuple/list.
Отключение tuple visitor устраняет наблюдаемый дефект, но теряет правильное
форматирование настоящего tuple. Поэтому такое отключение не является ремонтом.

В отдельной копии ассистент написал диагностическую правку `visit_Tuple`:
перед назначением изменения проверяется, содержит ли найденная пара скобок
последний элемент Tuple. Изменён только `_plugins/literals.py`.
Одинаковая native-выборка: **127 passed / 7 failed / 1 xfailed →
134 passed / 0 failed / 1 xfailed**. Корпус неизменен. Это проверка выбранного
места и механизма на известной задаче, а не автономный ремонт COS, не модельный
кандидат и не проверка всех поддерживаемых версий Python.

Evidence: `artifacts/repair_scope_20260923/causal-trace.json`,
`location-verification.json`, `assistant-location.patch`, парные `*-probe.json`.
Скрипты `trace_formatter.py` и `check_location.py` находятся рядом.
Новых LLM-запросов нет, внешний inference расход этого этапа — 0.

## Изменение COS

Новый пакет failure evidence сохраняет `target_binding_evidence`: способ
привязки, наблюдаемый target и явное `root_cause_proven=false`.
Старые пакеты остаются читаемыми; отсутствие provenance не превращается
в подтверждённую причину. Исторические пакеты и их digest не переписаны.

Диагноз поддерживает альтернативный ответ `target`, `failure_signature`,
`scope_review`: причина пересмотра, до четырёх предполагаемых функций и список
недостающих доказательств. Он не требует придумывать mutation contract.
Имена функций — непроверенные предложения для исследования, а не разрешение
на редактирование. Проверяются идентичность задачи, структура, размеры и отсутствие
полей с патчем/полномочиями. Смешанный ответ с одновременно scope review и
ремонтным планом отклоняется.

Валидный ответ получает `scope_review_required`; repair design и executable
authority не создаются. Ремонтный pipeline сохраняет объяснение, возвращает
задачу Analyzer, не запрашивает кандидата и не запускает автоматический повтор.
Обычная ветка гипотез и прямой режим предложений сохраняются. Контракт помогает
модели признать недостаточность области; он **не обнаруживает автоматически**
все неверно выбранные функции и не гарантирует, что модель им воспользуется.

Ранее существовавший `repair_target_nomination` уже различал API и место ремонта,
но ограничен методами одного класса/экземпляра. Межмодульные callback этого кейса
в тот контракт не помещаются. Его ограничения не ослаблены, ручное имя функции
не выдаётся за проверенную автоматическую номинацию.

## Проверки и продолжение

Регрессии проверяют обе альтернативы схемы, сохранение идентичности, запрет
смешанных ответов/полномочий, отсутствие второго модельного вызова и передачи
кандидата на исполнение. Дополнительно проверены прежние nomination/trial,
assertion plans, передача между ролями и ограниченные правки соседних методов.
JUnit: `artifacts/repair_scope_20260923/tests.xml`, `consumers-tests.xml`;
заключительная проверка — stage receipt инструмента `development_stage finish`.

Следующий полезный этап: ограниченная, привязанная к исходникам номинация
обычных функций и callback между модулями, с сохранением исходного API evidence.
Затем один ограниченный модельный ремонт в доказанной области с прежней полной
native-приёмкой. Не повторять старый prompt, не подставлять этот ручной патч
в модельный результат. Подтверждённый humanize результат сохраняется; новых
численных оценок ролей этот этап не даёт.
