Область: передача задачи и аудит происхождения выводов. Это завершение
инженерного этапа, не всего плана 9.7+. Шесть случаев созданы ассистентом для

требования. Это не независимый корпус и не реальные новые проекты.

Исходный запуск всех шести случаев выбирал `minimal_safe_extraction` и терял
структурированный контракт задачи между Analyzer и Architect. Цель в тексте
не обеспечивала требований в спецификации. Источник:
`artifacts/verification/upstream_baseline_20260913.json` (снимок до интеграции).

| Роль | Изменение | Что ещё не подтверждено |
|---|---|---|
| Analyzer | Контракт задачи, точные Python-символы и хеши, явные конфликты значений одного ограничения, происхождение фактов | Самостоятельное понимание свободного текста, поиск причин и противоречий произвольного смысла |
| Architect | Предложения по типу задачи: локальное изменение, разделение за существующим API, уточнение; устаревший анализ требует повторения | Выбор на основе проверенного причинного диагноза, влияние на callers, конкретный механизм изменения |
| SpecWriter | Все переданные требования остаются MUST, примеры acceptance и связь с требованиями сохраняются, пробелы видимы | Самостоятельное получение достаточных acceptance-тестов и исполнимого ImplementationDelta |

Поле происхождения отличает статические наблюдения, правила, вход пользователя
и диагностическую помощь ассистента. Существующие policy confidence не являются
калиброванной вероятностью правильного решения. Обычная цель без `task_contract`
сохраняет прежний маршрут; новый интерфейс не извлекает требования из произвольного
текста автоматически.

## Использование и границы

`analyze_role_project(..., task_contract=...)` и
`run_role_pipeline(..., task_contract=...)` принимают `upstream_task_contract.v1`.
CLI: `tools/role_pipeline_run.py --task-contract <workspace-relative.json>`.
Контракт задаёт `origin`, `change_kind`, список `requirements` с уникальными `id`,
`statement`, `targets` вида `core.py:Class.method`, `acceptance_examples` и
`constraints` с `key`/`value`. Примеры находятся в
`evaluation/upstream_roles/manifest.json`.

Этот новый маршрут пока предназначен для планирования: исполнение/transform
отклоняются, Reviewer требует завершить дизайн. Даже переданный готовый дизайн
не становится автоматически проверенным. Старые проверенные маршруты ремонта
и greenfield имеют свои контракты и сохраняются.

`build_upstream_feedback` возвращает адресные запросы ролям, допускает не более
двух итераций и сверяет привязку наблюдений к источнику. Содержимое внешнего receipt
по его digest самостоятельно не проверяет. Это API обратной связи, не фоновый
агент и не автоматическое повторное рассуждение. Пилот вызывает его явно.

Повтор пилота: `python tools/upstream_role_pilot.py --output <новый receipt.json>`.
Исходный manifest проверяется по хешам, прежний receipt не перезаписывается.

## Следующий результат

Приоритет `upstream-causal-design`: связать существующий causal evidence packet
с проверкой нескольких гипотез Analyzer; Architect должен обосновать конкретные
изменения и неизменяемые свойства; SpecWriter — сформировать delta и исполнимые
acceptance. Выход: реальный development-пример через всю цепочку без ручной записи
засчитываемого диагноза/patch. Затем перенос и новый независимо оцениваемый набор.
Перед новым сравнением моделей остаются нужны достоверные расходы шлюза и
независимый судья. Исторические оценки ролей не пересчитаны.
