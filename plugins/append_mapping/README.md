# Append-mapping boundary competency

Owner of `nested_loop_mapping_boundary` and its source contrast. They describe
the boundary of extracting a dictionary-building helper from an append loop.
The records retain their staged status, evidence, predicates and provenance.
Plugin lifecycle `active` permits registered read-only calls; it does not promote
the contained knowledge or authorize patching.

Operations: `boundary_profiles`, `source_contrasts`, `decorate_profile`, `propose_patch`,
`patch_recipes`, `propose_helper`. `decorate_profile` preserves the supplied owned profile without an activation overlay.
KB reads are fresh; the registry identity includes local knowledge. Existing
generic provider dispatch and the boundary interpreter require no domain branch.

Version 0.2.0 owns the executable reducer in `src/extractor.py`. `propose_patch`
accepts `source`, `origin_symbol`, `proposed_symbol`, `maximum_mapping_fields`;
it returns `proposed` with the original patch dictionary, or `not_applicable`
with null patch. Source is supplied as text, never executed or applied here.
The algorithm, unsupported shapes and limits retain their previous semantics.
`runtime.append_mapping_contract` checks registered identity and operation output;
recovery and development consumers keep their sandbox and differential gates.
The old extractor import delegates to that same client.

Neutral `parent_map` and `find_top_level_function` are shared through
`cognitive_inspect.ast_navigation`. The existing compatible parser is also owned
by Inspect. `implementation_packages` binds its installed source into plugin
identity; shared imported dependency changes require restart even after registry
refresh. Owner-specific loop and accumulator checks stay in this plugin.
Version 0.3.0 owns the extraction recipe in `knowledge/patch_recipes.json`.
`patch_recipes` returns `ok` and records with `id` and the unchanged `recipe`.
Limits, differential inputs and required checks have one mutable source here.
The installed policy composes registered contributions and rejects duplicate IDs;
explicit file loading validates only the supplied policy document. Recipe reads
are fresh and integrity checked. Selection among reducers and application gates
remain in recovery/development; a recipe does not authorize source mutation.

Version 0.4.0 adds `propose_helper` with the same source/symbol/limit inputs.
It returns `ok` and a `helper_proposal.v1` envelope. `src/proposal.py` owns
append metadata and refusal reason; `propose_patch` retains its original shape.
The runtime client validates the common proposal envelope; recovery owns target,
path, operation identity, compile, write and verification. No runtime imports
or source writes are added to this plugin.

`guard_mapping_path_descent` concerns early returns during path lookup and is a
different mechanism; it is not part of this competency. Generic ambiguity and
unsupported-shape fallback records remain in the shared protocol catalog.
